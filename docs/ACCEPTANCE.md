# Живая приёмка

Всё, что нельзя проверить без действующей подписки «Гаранта», проверяется
здесь — один раз, руками владельца подписки. Агенты в этой процедуре
не участвуют и участвовать не могут: она открывает окно входа в подписку
и трогает работающего демона.

**Пока эта приёмка не пройдена, этап не закончен.** Репозиторий при этом
публикуется раньше неё — по решению владельца (решение 34): единственная
чистая машина, где приёмку можно пройти, — второй компьютер, и ставить туда
он будет с публичного адреса, как посторонний. Чего это стоит, сказано там
же: до приёмки установку с чистой машины не проверял никто, кроме
изолированного прогона в среде разработки, и первым посторонним читателем
может оказаться не владелец.

---

## Прежде чем начать

**Отведите полдня и не начинайте в спешке.** Суммарно это три-четыре часа
на две машины (оценка, не замер): установка с загрузкой браузера — до
получаса; пункт 3 требует ждать закрытого клиента больше получаса; пункт 7а —
девять вопросов с поиском подходящих актов — около часа; пункт 8 — сеанс
записи по всем инструментам — полчаса; остальное — по нескольку минут.
Половина пунктов необратима не технически, а по времени: если что-то пойдёт
не так посреди, придётся входить в подписку заново; брошенная посередине
приёмка записывается как «не проверял».

**Что здесь про риск.** Единственная вещь, которую больно потерять, —
профиль браузера с вашим входом. Ни один пункт ниже его не удаляет; команда,
которая может, требует отдельного флага и подтверждения. Но прежде чем
начать, знайте, где он лежит: `garant status` печатает каталог состояния,
профиль — внутри него.

**Что записывать по ходу.** У каждого пункта есть исход: **да**, **нет**
или **не проверял**. Записывайте буквально, вместе с текстом ошибки, если
он был. «Вроде заработало» — не исход: именно из таких формулировок берутся
дефекты, которые потом ищут неделю.

### Где какой пункт проходится

Половина пунктов привязана к машине владельца, потому что предмет проверки —
именно то, что на ней уже есть. Остальные проверяют продукт как таковой,
и второй компьютер для них лучше: там нет ни старых переменных окружения,
ни следов прежних установок, и «работает» означает работает у постороннего.

| пункт | где |
|---|---|
| 0. вывести из работы старую установку | **только эта машина** — старой установки больше нигде нет |
| 1. установка с чистой машины | **второй компьютер** (или новый пользователь Windows / песочница) |
| 2. инструменты в Claude | второй компьютер |
| 2а. инструменты в Codex | любая машина, где установлен Codex; необязательно |
| 3. сессия переживает закрытие клиента | второй компьютер |
| 4. перенос профиля со старой установки | **только эта машина** — источником служит старая папка |
| 5. обновление не стоит повторного входа | второй компьютер |
| 6. удаление говорит правду | **только эта машина**, под тестовым пользователем или в песочнице; на втором компьютере — последним, после 1, 2, 3, 5, 7 и 8, иначе проверять будет нечем |
| 7. открытый вопрос о редакции на дату | второй компьютер (нужна любая рабочая установка) |
| 7а. девять вопросов о разметке и периодах действия | второй компьютер (там же, сразу за пунктом 7) |
| 7б. замер остановки демона | любая машина с рабочей установкой |
| 8. записать образцы для тестов | второй компьютер |

Порядок: 0 здесь, потом 1–3 и 5, 7, 7а, 7б, 8 там, потом 4 и 6 здесь.

**Требования к любой из машин:** действующая подписка «Гаранта», установленный
Claude Desktop или Claude Code, установленный `git` (пакет ставится из
git-репозитория, без git установщик остановится и скажет об этом).

## Пункт 0. Вывести из работы старую установку

**Где:** только эта машина. **Делается до всего остального** и один раз.

Команды ниже — команды нового пульта `garant`. Если он на этой машине ещё
не находится (`garant --version` молчит), сначала поставьте пакет здесь
командой из README, шаг 1; окно входа при этом можно закрыть — вход на этой
машине понадобится только в пункте 4.

На машине владельца живёт установка, сделанная прежним установщиком: задача
планировщика, демон из старой папки и регистрации у MCP-клиентов, указывающие
туда же. Задача планировщика прежней установки была снята 06.09.2026
(`docs/TEAM.md` §4) — если `doctor` показывает автозапуск зелёным «не стоит»,
это норма, а не ошибка; снимать остаётся регистрации, указывающие в старую
папку. Пока она работает, новая установка будет спорить с ней за монопольный
профиль браузера, а вы будете видеть необъяснимые отказы.

**Команды:**

```
garant doctor
garant autostart off
garant unregister
```

1. `garant doctor` покажет задачу планировщика прежней установки красным
   пунктом «автозапуск»: имя записи у старой и новой установки одно
   и то же — `GarantDaemon`, — поэтому новый пульт её видит, опознаёт как
   ведущую не туда и называет команду. Остановите старого демона тем
   способом, которым запускали его тогда.
2. `garant unregister` снимает запись `garant` у Claude Desktop и Claude Code
   (и у Codex, если вы её регистрировали ключом `--codex`).
   Плагин `garant`, если он у вас заведён, либо снимите, либо переведите
   на `{"command": "garant-mcp"}` — он не входит в этот репозиторий и сам
   не обновится.
3. **Старую папку не удаляйте.** Она пригодится в пункте 4 как источник
   профиля и как страховка: пока новая установка не ответила на запрос
   к «Гаранту», старый вход — единственный, который у вас есть.

**Ожидаемое:** старый демон не работает, задачи планировщика нет,
регистрации сняты.

**Записать:** исход да / нет; если `doctor` после `autostart off` всё ещё
показывает автозапуск красным — текст пункта дословно.

## Пункт 1. Установка с чистой машины

**Где:** второй компьютер, либо новый пользователь Windows, либо песочница.
Если это невозможно, годится и обычный сеанс, но результат слабее: вы
проверяете установку на машине, где половина уже стоит.

Проверяется то, ради чего затевался этап: **три шага и без нашего участия.**

**Команды** — ровно те, что в README, и ничего сверх них:

```
powershell -NoProfile -ExecutionPolicy Bypass -Command "& ([scriptblock]::Create((irm https://raw.githubusercontent.com/semenboss95-design/garant-mcp/main/install.ps1).TrimStart([char]0xFEFF)))"
```

на macOS и Linux:

```
curl -LsSf https://raw.githubusercontent.com/semenboss95-design/garant-mcp/main/install.sh -o install.sh && sh install.sh
```

Затем вход в открывшемся окне руками и перезапуск Claude.

**Ожидаемое** — три вещи, и смотреть надо на все три:

* **установщик дошёл до конца и напечатал, что сделал.** Сводка «сделано /
  пропущено / не удалось» — обязательна;
* **код возврата ноль только если сделано всё.** Проверить сразу после
  установки: в PowerShell — `$LASTEXITCODE`, в оболочке — `echo $?`. Если
  что-то не удалось, а код нулевой, это дефект, и он важнее того, что именно
  не удалось: ровно так прежний установщик печатал «ок» после двух ERROR;
* **`garant doctor` зелёный целиком.** Красный пункт обязан нести команду
  починки. Красный пункт без команды — тоже дефект.

Отдельно проверьте, что установщик **назвал отсутствие git заранее**, если
git на машине нет: он обязан сказать это до попытки установки, а не упасть
сообщением пакетного менеджера.

**Записать:** да / нет; при «нет» — на каком из четырёх шагов установщика,
что было написано под строкой `[X]`, и число в `$LASTEXITCODE`.

## Пункт 2. Инструменты в Claude

**Где:** второй компьютер, после перезапуска Claude Desktop.

**Что сделать:**

* спросите Claude вызвать `garant_kinds` — он обязан вернуть дерево видов
  информации;
* спросите текст любой знакомой вам статьи (`garant_article`) — он обязан
  вернуть текст **и блок `provenance`**: редакция, дата начала её действия,
  изменяющий акт, источник, дата проверки, отпечаток текста.

Смотреть надо на провенанс, а не на текст. Текст вы и так узнаете; смысл
инструмента в том, что рядом с ним стоит проверяемая ссылка на редакцию.

**Проверьте отпечаток руками.** Это третья проверка пункта, и она главная:
до этого этапа хеш считался не над тем текстом, который отдавался, и никто
этого не замечал, потому что никто не проверял.

Отпечаток — не полный sha256, а **первые 16 шестнадцатеричных знаков** sha256
от значения ключа `text` в кодировке UTF-8, с префиксом `sha256:`. Полный хеш
с ним не сойдётся никогда, и это не дефект.

Windows, PowerShell:

```
garant call article doc_id=12125178 article=97 | Set-Content -Encoding UTF8 otvet.json
python -c "import json,hashlib;d=json.load(open('otvet.json',encoding='utf-8-sig'));print('sha256:'+hashlib.sha256(d['text'].encode('utf-8')).hexdigest()[:16])"
```

macOS и Linux:

```
garant call article doc_id=12125178 article=97 > otvet.json
python3 -c "import json,hashlib;d=json.load(open('otvet.json',encoding='utf-8'));print('sha256:'+hashlib.sha256(d['text'].encode('utf-8')).hexdigest()[:16])"
```

Если ни `python`, ни `python3` в PATH нет (uv ставит свой Python и в PATH его
не выносит), то же самое даёт `uv run --no-project python -c "…"`.

Напечатанную строку сравните с ключом `hash_текста` — он лежит в том же
файле `otvet.json`, внутри блока `provenance`. `doc_id` и номер статьи берите
свои: 12125178/97 — просто пример из справки пульта.

**Ожидаемое:** обе строки совпадают знак в знак.

**Записать:** да / нет по каждому из трёх (kinds, article с провенансом,
сошедшийся отпечаток). При «нет» на отпечатке — обе строки целиком.

## Пункт 2а. Инструменты в Codex (необязательно)

**Где:** любая машина, где установлен Codex (агент OpenAI по подписке
ChatGPT). Пункт необязательный: без Codex его пропускают и записывают
«не проверял». Заведён 09.09.2026 (решение 40).

Это единственное утверждение про Codex, которое нельзя проверить без
самого Codex: что он действительно поднимает наш сервер по записи
`[mcp_servers.garant]` в `~/.codex/config.toml`. Всё остальное — что запись
пишется, чужие настройки не трогаются, копия `.bak` рядом, снятие честное —
проверено тестами и живым прогоном в изоляции.

**Команды:**

```
garant register --codex
garant doctor
```

Затем перезапустите Codex и спросите его что-нибудь правовое.

**Ожидаемое:** `doctor` показывает строку «Codex: зарегистрирован»; в Codex
появились восемь инструментов «Гаранта»; чужие записи в `config.toml`
остались на месте.

**Записать:** да / нет; появились ли инструменты; текст ошибки Codex, если
была; при «нет» — вывод `garant doctor` целиком и содержимое `config.toml`
без чужих секретов.

## Пункт 3. Сессия переживает закрытие клиента

**Где:** второй компьютер. Смысл демона в том, что подписка не отваливается,
когда вы закрыли Claude.

**Что сделать:**

1. Закройте Claude полностью.
2. Подождите **больше получаса** — это заметно дольше, чем живёт cookie
   продления (единицы минут; продление идёт раз в 120 секунд).
3. `garant status`.
4. Откройте Claude и вызовите `garant_kinds`.

**Ожидаемое:** `garant status` печатает «демон: работает» и «сессия: жива»,
инструмент отвечает без повторного входа.

**Это и есть та проверка, которую нельзя сделать без вас.** Всё, что мы можем
здесь, — убедиться, что демон честно отчитывается о том, что с ним
происходит; сработает ли продление против настоящего «Гаранта», знает только
живая подписка.

**Записать:** да / нет. При «нет» — вывод `garant status` целиком и последние
строки `garant logs`.

## Пункт 4. Перенос профиля со старой установки

**Где:** только эта машина — источником служит старая папка из пункта 0.

```
garant stop
garant migrate ПУТЬ_К_СТАРОЙ_ПАПКЕ
garant start
garant doctor --живой
```

Путь можно указывать и на каталог старой установки, и прямо на каталог
профиля: команда сама ищет профиль в четырёх местах внутри указанного
и, если не нашла, печатает список мест, где искала.

**Ожидаемое** — три вещи, за которыми надо проследить:

* **оригинал не тронут.** Команда делает копию и говорит об этом отдельной
  строкой «оригинал не тронут: …»; старая папка после неё обязана остаться
  такой же;
* **демон был остановлен.** Если демон работает, `migrate` обязан отказаться,
  а не копировать: перенос профиля Chromium на ходу ломает профиль, и лечится
  это тем самым повторным входом, которого мы избегаем;
* **отпечаток.** Команда переносит файл отпечатка старой установки вместе
  с профилем, а свой откладывает рядом в `.bak`. Если у старой установки
  отпечатка не было, она об этом говорит вслух — и тогда первый же запрос
  может дать «сессия недействительна». Это не поломка: войдите заново через
  `garant login`. Старый профиль при этом цел.

**Записать:** да / нет / не переносил; сколько файлов и мегабайт назвала
команда; что она сказала про отпечаток.

## Пункт 5. Обновление не стоит повторного входа

**Где:** второй компьютер.

```
garant update
```

**Ожидаемое:** команда называет, чем поставлен пакет (uv или pipx), обновляет
его, перезапускает демона, заканчивает диагностикой, и **вход в подписку
не требуется**. Последнее — главное: если обновление стоит ручного входа,
им не будут пользоваться, и через месяц у вас снова будет установка
неизвестной давности.

Отдельный законный исход: команда не выяснила, чем поставлен пакет, и
**ничего не тронула**, назвав команду обновления руками. Это не отказ
приёмки, но запишите его — он означает, что установка сделана не через
`uv tool` и не через `pipx`.

**Записать:** да / нет; чем поставлен пакет по словам команды; потребовался
ли вход после.

## Пункт 6. Удаление говорит правду

**Где:** эта машина, **под тестовым пользователем или в песочнице**, не
на рабочем профиле. На втором компьютере — только последним, после всех
остальных пунктов.

```
garant uninstall
```

**Ожидаемое:** команда сначала печатает, что именно будет снято и что станет
с профилем, и спрашивает подтверждение (`y`). Затем: остановлен демон, сняты
регистрации у Claude Desktop и Claude Code, снят автозапуск; напечатан раздел
**«ОСТАЛОСЬ НА МАШИНЕ»** — каталог состояния, кэш браузеров playwright и сам
пакет с командой его снятия. **Профиль браузера не тронут** — он удаляется
только с ключом `--purge` и только после отдельного ответа «удалить».
Повторный запуск не ошибка.

Проверьте отдельно, что регистрации в `.mcp.json` конкретных проектов команда
**не** трогает и честно об этом говорит: она их не видит.

**Записать:** да / нет; список из раздела «ОСТАЛОСЬ НА МАШИНЕ»; цел ли
профиль после.

## Пункт 7. Открытый вопрос о редакции на дату (решение 12)

**Где:** второй компьютер, любая рабочая установка.

Единственный пункт, который не проверяет продукт, а **отвечает на вопрос**,
от которого зависит форма ответа двух главных инструментов.

`garant_revision_on_date` возвращает `id_редакции` — идентификатор самой
редакции. Мы не знаем, принимает ли его `garant_article` как `doc_id`.
Если принимает — текст нормы в нужной редакции достаётся существующими
средствами, и разрыв «редакция установлена, а текста в ней нет» закрывается.

**Как проверить:**

1. Возьмите статью, которая **заведомо менялась** между редакциями. Статья,
   не менявшаяся много лет, даст совпадение текстов и ничего не докажет.
2. `garant call revisions doc_id=ИДЕНТИФИКАТОР` — выпишите `id_редакции`
   недействующей редакции.
3. `garant call article doc_id=ID_РЕДАКЦИИ article=НОМЕР`.
4. Сравните **отпечатки текста и заголовки**, а не первые строки на глаз:
   `hash_текста` из этого ответа против `hash_текста` из ответа по обычному
   `doc_id`.

Через Claude то же самое делается словами; `garant call` предпочтительнее
тем, что параметр уходит буквально таким, каким вы его написали.

**Три возможных исхода, и все три — ответ:**

* вернулся текст **той** редакции (отпечатки разошлись, заголовок редакции
  соответствует) — мост работает;
* вернулся текст действующей редакции (отпечатки совпали) — моста нет,
  и это опаснее отказа: ответ выглядит правильным;
* ошибка — моста нет, и это честно.

Отдельно выполните `garant call revisions doc_id=ID_РЕДАКЦИИ`: если он ведёт
себя как документ, у него есть своя история редакций, и это тоже ответ.

**Записать:** какой из трёх исходов; оба отпечатка; текст ошибки, если была.

## Пункт 7а. Девять вопросов о разметке и о периодах действия

**Где:** второй компьютер, любая рабочая установка. Заведён 07.09.2026,
этап 03.

Это не проверка продукта, а девять вопросов, ответить на которые в среде
разработки нечем: подписки там нет, а весь разбор текста нормы держится
на предположениях о том, как «Гарант» размечает страницу. Пока ответов нет,
код сделан так, чтобы ошибка была громкой, — но правильность непроверяема.

**Вопрос 1. Есть ли в HTML статьи надстрочные индексы и таблицы.**
Возьмите статью, в номере которой есть индекс (вида «статья 5¹») **или**
норму с табличной формой. Запросите `garant call article doc_id=…
article=…` и посмотрите на текст.

*Ожидаемое:* индекс отделён кареткой — `ст. 5^1`, а не `ст. 51`; ячейки
таблицы разделены ` | `, а не слиты в одно слово.

*Записать:* попался ли вообще такой текст; как он выглядит дословно.
Если индексы в разметке не `<sup>`, а что-то иное, — `strip_html/2` чинит
не то, что сломано, и это надо знать.

**Вопрос 2. Как «Гарант» трактует границу периода действия.**
Мы читаем её **включительно**: дата, равная концу одного периода и началу
следующего, считается подходящей обеим редакциям, и в таком случае ответ
несёт `_предупреждение`. Это наша конвенция, а не установленный факт.

`garant call revision_on_date doc_id=… on_date=ДАТА_СТЫКА` — дата берётся
из `garant call revisions doc_id=…`, поле конца одного периода.

*Записать:* пришло ли `_предупреждение` о двух кандидатах, и совпал ли
выбор с тем, что показывает сам «Гарант» в браузере на ту же дату.
Если «Гарант» читает границу исключающе — предупреждение выдаётся там,
где неоднозначности нет, и лишний кандидат наш.

**Это самый дешёвый вопрос из девяти и самый ценный.** От ответа зависит
не одна формулировка, а целая ветвь кода. Периоды `по 31.12.2020` и
`с 01.01.2021` мы считаем непрерывными — но только потому, что читаем
границу включительно. При исключающем чтении 31.12.2020 не покрыт ничем,
и это **дыра в действии нормы длиной в сутки**. Сегодня инструмент в таком
случае говорит, что непрерывность держится на нашем чтении, и помечает
её непроверенной; ответ на этот вопрос либо убирает оговорку целиком, либо
превращает суточную дыру из гипотезы в дефект, который надо чинить.

*Как ответить точно:* возьмите акт, где конец одного периода и начало
следующего отличаются на один день, и спросите `revision_on_date` на дату
**конца** первого периода. Затем посмотрите ту же дату в окне подписки:
какую редакцию показывает сам «Гарант». Запишите обе.

**Вопрос 3. Акт с прерванным действием.**
Найдите акт, действие которого приостанавливали и возобновляли (у такого
в `garant call revisions` несколько периодов в одной редакции).

*Записать:* сколько периодов пришло в ключе `периоды`; что стоит
в `действует_с` и `действует_по` при запросе на дату **второго** периода
(должен быть второй период, а не первый); есть ли оговорка о прерывании
в `оговорки_о_редакции`.

**Вопрос 4. Подстрочный индекс в формулах.** В нормах с формулами (налоговые
коэффициенты) переменные пишутся подстрочным индексом: `К_д`. Возьмите такую
норму и посмотрите, разделён ли индекс в выдаче или слит в `Кд` — это разные
переменные, и склейка здесь того же рода, что «ст. 5¹» → «ст. 51».

*Записать:* дословно, как выглядит переменная с индексом.

**Вопрос 5. Встречается ли символ `|` в тексте самих актов.** Мы разделяем
им ячейки таблицы, и отличить наш разделитель от такого же символа в акте
по цитате нельзя. Дополнительно: хвостовой `|` мы снимаем — если он стоял
в самом акте, цитата изменена.

*Записать:* попадался ли `|` в тексте норм; в каком контексте.

**Вопрос 6. Ячейки без закрывающего тега.** Разметка часто небрежна: если
`<td>` не закрыт, разделитель не подставится и ячейки снова склеятся —
молча.

*Записать:* видно ли в выдаче слитые ячейки там, где в браузере таблица.

**Вопрос 7. В каком порядке приходят периоды действия.** Возьмите акт,
у которого в `garant call revisions doc_id=…` несколько периодов, и посмотрите,
идут ли даты по возрастанию или по убыванию.

*Почему это важнее прочих:* расчёт разрыва в действии сравнивает соседние
периоды по датам. При убывающем порядке настоящий перерыв не находится
арифметически. Код на этот случай отвечает «установить нечем» и говорит
об этом вслух — но пока порядок не выяснен, `revision_on_date` на таких
актах молчаливой уверенности не даёт и давать не должен.

*Записать:* порядок дат в ответе, дословно.

**Вопрос 8. Какие формы приходят в границах периодов, и бывает ли пустой
конец не у последнего элемента.** Мы читаем пустое — пустую строку, null,
ноль, пустой список — как отсутствие границы, для конца это «бессрочно»;
непустое нестроковое (число, список, объект) — как границу, которую прочесть
нечем (решение 36). Всё это прочтение, а не знание: какие формы «Гарант»
присылает на самом деле, не видел никто. И если пустой конец бывает
не у последнего элемента — означает он «бессрочно» или «поле не заполнено»?
Это разные вещи, и по ответу отличить их нельзя.

*Записать:* по нескольким актам — что стоит в `периоды` ответа
`garant_revisions` дословно, включая тип значения (строка / число / список /
null / поля нет); попадался ли пустой конец не у последнего элемента; что
стоит в соседних полях.

**Вопрос 9. Сверить прочтение «приостанавливали и возвращали в силу».**
Найдя акт с настоящим разрывом, откройте его карточку в окне подписки и
посмотрите, что там сказано о причине перерыва. Сегодня это гипотеза,
и она уезжает пользователю помеченной как непроверенная.

*Записать:* что говорит карточка.

**Почему это отдельный пункт, а не строка в отчёте.** Все девять вопросов
07.09.2026 были помечены исполнителями как «непроверено: требует живой
подписки». Помеченное непроверенным и не переданное тому, кто может
проверить, через неделю становится проверенным само собой — по забывчивости.

## Пункт 7б. Остановка демона: сколько заняла и что осталось жить

**Где:** любая машина с рабочей установкой. Заведён 07.09.2026, этап 03.

Единственный пункт, где мы просим **замер**, а не «да/нет». Причина: демон
на остановке закрывает браузер, и потолок на это выбран **по факту прежних
чисел, а не измерен**. Сами числа здесь не пишем — они живут в одном месте,
`src/garant_mcp/protocol.py` (`ПОТОЛОК_ОСТАНОВКИ_СЕК`, и из него выводится
потолок уборки; решение 33), и переписанные сюда прописью они протухли бы
молча. Если закрытие занимает дольше потолка уборки — демон уходит,
оставив запись в журнале, а chromium продолжает держать профиль подписки.

Со стороны пульта закрытие браузера **не видно**. С 08.09.2026 `garant
stop` ждёт не молчания порта, а смерти процесса, и печатает один из трёх
исходов (решение 35): процесс ушёл (код 0; в тексте PID, порт, секунды
и отсылка к `garant logs`); демон замолчал, но процесс к потолку жив
(код 1; `daemon_port` остаётся); демон продолжает отвечать (код 1; окно
входа). До этого этапа он печатал «демон остановлен», хотя браузер мог
остаться.

**Как проверить:**

1. Убедитесь, что демон работает и вход выполнен: `garant status`.
2. Заметьте время и выполните `garant stop`.
3. Сразу после — посмотрите, остались ли процессы браузера:
   на Windows `Get-Process chrome*, chromium* -ErrorAction SilentlyContinue`;
   на macOS и Linux `ps aux | grep -i chrom`.
4. Загляните в журнал: `garant logs` — последние строки. Демона уже нет,
   поэтому журнал читается с диска; пометка об этом печатается в stderr,
   отдельно от строк журнала, — перенаправив вывод в файл, вы её не
   увидите, и это нормально.

**Записать:**

* сколько секунд заняла команда `garant stop` (хватит секундомера телефона);
* остались ли живые процессы браузера **после** её завершения;
* есть ли в журнале строка о том, что браузер не закрылся штатно;
* что напечатал сам `garant stop` — дословно.

**Почему это важнее, чем кажется.** Осиротевший chromium держит
`chrome_profile`, а профиль — это и есть живая сессия подписки. Следующий
запуск демона упрётся в занятый профиль, и человек увидит отказ, причина
которого случилась минутой раньше и в другом месте.

Если замер покажет, что потолка уборки (число — в `protocol.py`, см. выше)
мало, — это не «подкрутить число», а наряд: закрытие браузера надо либо
ускорить, либо перестать обещать.

## Пункт 8. Записать образцы для тестов

**Где:** второй компьютер, один раз, пока подписка под рукой.

Запись включается переменной окружения, а читает её **демон в момент своего
запуска**. Поэтому переменную мало задать: демона надо перезапустить из того же
окна консоли, иначе он останется без неё и не запишет ничего.

Windows, PowerShell:

```
garant stop
$env:GARANT_RECORD = "1"
garant start
```

macOS и Linux:

```
garant stop
export GARANT_RECORD=1
garant start
```

Затем выполните обычную работу — по одному вызову каждого инструмента: поиск,
оглавление, статья, документ, редакции, практика. Через Claude или через
`garant call`, разницы для записи нет: в «Гарант» ходит один и тот же демон.

Снять запись — тем же способом, иначе она продолжится:

```
garant stop
$env:GARANT_RECORD = ""        # macOS/Linux: unset GARANT_RECORD
garant start
```

**Ожидаемое:** сырые тела ответов легли в каталог `recordings` внутри каталога
состояния (`garant status` печатает его путь). Каталог закрыт `.gitignore`
и в репозиторий не попадёт — **тексты актов не публикуются никогда.** Эти
записи дают тестам то, чего не даёт никакая синтетика: настоящую разметку
страниц, от которой зависит вырезка статьи и нормализация HTML.

**Записать:** записано / не записано; сколько файлов появилось в `recordings`.

## После приёмки

Сведите исходы в один список и передайте команде. Формат простой: номер
пункта — да / нет / не проверял — и текст ошибки, если была.

Дальше действует правило, которое здесь важнее вежливости: **пункт
с исходом «нет» закрывает этап.** Не «учтём в следующем» — закрывает.
Причина простая: следующего раза с живой подпиской может не быть неделями,
а всё, что здесь не проверено, проверит первый посторонний читатель.

**Автозапуск — отдельно, и он тоже только ваш.** `garant autostart on` требует
прав на создание задачи планировщика, которых в среде разработки не было,
поэтому проверить его могли только вы. Делается на любой из машин:

```
garant autostart on
garant autostart status
garant doctor
```

`status` сразу после `on` обязан ответить «стоит, запускает garant-daemon
из …». Если он вместо этого говорит, что запись с этим именем есть, но ведёт
не на `garant-daemon`, — это дефект разбора, и его надо назвать: он означает,
что диагностика красит красным работающую запись.
