# Архитектура garant-mcp

Одна страница о том, как устроена установка и почему именно так. Записано
05.09.2026 в начале этапа 02. Всё, что здесь описано как «стало», — целевое
состояние этапа; пока этап идёт, код местами ещё в состоянии «было», и такие
места названы прямо.

Подробности решений — `DECISIONS.md`, записи 14–22. Девять ограничений,
которые этап не отменяет, — `CLAUDE.md`.

---

## 1. Что такое «установка»

**Установка = установленный Python-пакет `garant-mcp` + один каталог
состояния + регистрация у MCP-клиента.** Всё остальное — копии кода, и им
запрещено что-либо о себе объявлять.

До этапа 02 понятия не было вовсе, а «указателей на активную установку» было
девять: две пользовательские переменные окружения, задача планировщика, ярлык
автозагрузки, три вида регистрации у клиентов, конфигурация плагина и каталог
состояния. Их писали разные скрипты, никто не сверял, и `GARANT_HOME` означала
«каталог кода» для установщика и «каталог состояния» для `paths.py`. Отсюда
рабочий симптом: правки уходят в одну копию, а инструменты работают из другой,
и человек об этом не узнаёт.

Стало три указателя, и каждый отвечает ровно на один вопрос.

| указатель | отвечает на вопрос | где живёт |
|---|---|---|
| исполняемые файлы `garant`, `garant-mcp`, `garant-daemon` в `PATH` | **каким кодом** исполнять | ставит `uv tool install` (или `pipx`) |
| каталог состояния — `platformdirs.user_data_dir("garant-mcp")` | **где** живут профиль, токен, порт, логи, кэш | вычисляет `paths.py`; переопределяется только `GARANT_HOME` |
| запись `{"command": "garant-mcp"}` в конфигурации клиента | **кто** запускает сервер | пишет `garant register` |

Ни один из трёх не содержит абсолютного пути. Это и есть главное свойство
раскладки: обновление пакета не требует переписывать ни одну регистрацию,
а регистрация не устаревает от переезда кода.

`GARANT_HOME` переопределяет **только каталог состояния** и ничего больше.
Прежняя эвристика «если рядом с кодом лежит профиль или токен — значит,
установка портативная» удалена: она угадывала намерение по следам и угадывала
неверно ровно тогда, когда копий кода становилось больше одной.

```
             ┌──────────────────────────────────────────────┐
   PATH ───► │ garant · garant-mcp · garant-daemon          │  код (только чтение)
             │ пакет garant-mcp в окружении uv tool / pipx  │
             └───────────────────┬──────────────────────────┘
                                 │ пишет только сюда
             ┌───────────────────▼──────────────────────────┐
             │ каталог состояния (каталог данных ОС)        │
             │   chrome_profile/   daemon_token  daemon_port│
             │   fingerprint.json  logs/  cache/            │
             │   endpoints.local.json   recordings/         │
             └──────────────────────────────────────────────┘
```

Каталог состояния отделён от кода не из аккуратности: пакет ставится в
каталог, который переустановка стирает. Профиль браузера с живым входом
в подписку, лежащий рядом с кодом, исчезал бы при каждом обновлении, и человек
входил бы заново.

`endpoints.local.json` — необязательный файл пользователя; он сливается
поверх пакетного `endpoints.json`. Существует ровно затем, чтобы обновление
пакета не затирало правку, которую человек сделал у себя.

## 2. Раскладка пакета

```
pyproject.toml                 имя garant-mcp, python >= 3.12
src/garant_mcp/
    __init__.py                __version__ — единственный источник версии
    paths.py                   каталог состояния, ensure_state()
    config.py                  env → endpoints.local.json → endpoints.json → умолчание
    protocol.py                признак демона, структура ошибок
    fingerprint.py             отпечаток браузера, снятый с машины
    client.py                  HTTP-клиент «Гаранта»; транспорт инъецируется
    daemon.py                  единственный владелец профиля браузера
    daemon_client.py           тонкий клиент; умеет поднять демона
    server.py                  MCP по stdio, восемь инструментов
    cli.py                     команда garant
    register.py                слияние конфигураций MCP-клиентов
    autostart.py               автозапуск при входе в систему — по желанию
    endpoints.json             карта эндпоинтов, БЕЗ отпечатка браузера
tools/                         конвейер реверса, вне пакета
tests/                         офлайн-тесты
install.ps1 · install.sh       установщики
```

Пульт на PowerShell (`garant.ps1` и четыре установочных скрипта) удаляется:
его работу делает `garant` на Python и делает на всех трёх ОС. История файлов
остаётся в git — см. решение 18.

## 3. Жизненный цикл демона

Ограничение 2 в силе: **один профиль браузера — один процесс**, и этот процесс
демон. Изменилось не это, а то, кто и когда его поднимает.

```
  MCP-клиент
      │ stdio
      ▼
  garant-mcp (server.py)
      │ первый вызов инструмента
      ▼
  GET http://127.0.0.1:<порт>/health
      │
      ├── ответил и признан нашим ──────────────► работаем
      │
      └── не ответил
              │
              ├─► запустить garant-daemon отсоединённым процессом
              │     Windows: без окна консоли;  POSIX: start_new_session
              │
              └─► ждать /health до 90 с (chromium стартует долго) ──► работаем
```

Раньше демон поднимался только задачей планировщика или руками, и если задачи
не было, инструменты не работали, а причина не называлась нигде. Теперь
автозапуск при входе в систему (`garant autostart on`) — удобство, а не
условие работы.

Гонку двух серверов, поднимающих демона одновременно, решает уже существующий
механизм: порт занимается биндом (решение 4), и второй демон, обнаружив на
порту нашего же, выходит кодом 0.

**Что демон отдаёт и кому.**

| путь | токен | что отдаёт |
|---|---|---|
| `GET /health` | не нужен | жив ли, признак демона, счётчики. **Ни путей, ни `последняя_ошибка`** |
| `GET /version` | не нужен | версия пакета и признак демона — и только |
| `GET /state` | нужен | состояние сессии, каталоги, последняя ошибка |
| `POST /call` | нужен | вызов метода из `ALLOWED` |
| `POST /login` | нужен | вход в подписку силами демона |
| `POST /probe`, `/restart`, `GET /logs` | нужен | как было |

Безтокенный `/health` очищен намеренно: он читается любым, кто может сделать
GET на петлю, а раньше носил `последняя_ошибка` с абсолютными путями машины.
Пути и состояние переехали под токен.

Сервер и демон сверяют версию. Сервер новее демона — сервер говорит
«выполните `garant restart`», а не работает молча на старом коде.

## 4. Вход в подписку

Вход остаётся ручным: «Гарант» авторизуется через OAuth, и окно браузера за
человека никто не заполнит. Изменилось, **кто открывает окно**.

```
было:  garant.ps1 вход → /restart демону → отдельный процесс auth_login.py
       → второй процесс на монопольный профиль → «демон будет остановлен»
         (неправда: демон продолжал работать и по таймеру снова открывал профиль)

стало: garant login → POST /login демону
       → демон сам закрывает headless-контекст
       → открывает ВИДИМОЕ окно на своём же профиле
       → человек входит
       → демон закрывает окно и возвращается в headless
```

Второго процесса на профиль больше не существует ни в одной точке; файл
`auth_login.py` удаляется. `login` добавляется в `ALLOWED` как внутренняя
операция демона, доступная только под токеном и только с петли — единственное
расширение белого списка за этап.

## 5. Отпечаток браузера

Ограничение 3 не отменяется: сессия «Гаранта» привязана к отпечатку, и окно
входа с рабочим контекстом обязаны совпадать. Меняется **источник значений**.

```
было:  endpoints.json → browser_profile → UA, locale, timezone_id, viewport
       Значения сняты с машины автора и уезжают в каждый клон:
       один опознаваемый отпечаток на все установки — и регион автора вдобавок.

стало: первый вход
         UA        ← настоящий chromium этой машины (HeadlessChrome → Chrome)
         locale    ← ОС
         timezone  ← ОС
         viewport  ← 1440×900
       записывается в <состояние>/fingerprint.json
       и вход, и работа читают ЭТОТ файл
```

Пока файл существует, значения не меняются — даже если ОС сменила часовой
пояс. Иначе смена пояса означала бы `Unauthorized` и повторный ручной вход.
`garant doctor` показывает отпечаток и **предупреждает**, если он разошёлся
с ОС; это предупреждение, а не ошибка.

Из `endpoints.json` секция `browser_profile` теряет значения; остаётся только
имя каталога профиля.

## 6. Ошибки и состояние

Правило одно: **инструмент не выдаёт себя за то, чем не является.**

* Ошибки между потоком браузера и HTTP-слоем ходят структурой
  `{"тип", "сообщение", "http"}` из `protocol.py`. `GarantError` несёт тип:
  `session`, `api_changed`, `not_found`, `browser`, `timeout`. Прежний признак
  истечения — поиск подстрок «401», «403», «сесси» в тексте любого
  исключения — объявлял сессию мёртвой на запросе «статья 401.11» и не ловил
  «Сессия…» с заглавной.
* `сессия = жива` — только после реального похода в «Гарант», не из кэша.
  `сессия = недействительна` — только по 401/403, пережившему повтор. Таймаут
  и сетевые ошибки состояние сессии **не трогают**.
* keepalive возвращает исход; демон пишет его в лог и в поле
  `последний_keepalive_исход`. В состояние `сессия` он не пишет никогда:
  «Гарант» отвечает 403 на живой сессии при холодном старте, и честный
  keepalive объявил бы её мёртвой по гонке, которую код сам признаёт.
* Ответ инструмента с ошибкой — **ошибка MCP** (`isError`), а не строка с
  ключом «ошибка», которую клиент не отличит от данных.
* В тексте ошибки нет путей **машины автора** и нет путей к коду: команда для
  человека всегда вида `garant <что-то>`, потому что `garant` лежит в `PATH`.
  Одно исключение осознанное: сообщение «токена нет» называет каталог,
  **где искали**, и каталог состояния пользователя. Это его собственный путь
  и единственный способ отличить «демон не запускался» от «демон запущен
  из другой установки»; в безтокенный `/health` он не уходит.
* `garant status` и `garant doctor` печатают ровно то, что доказано, и
  называют, что не проверялось.

## 7. Команда `garant` — единственный пульт

**Написана 06.09.2026** (шаги 3 и 4). Не проверено живой подпиской: `login`,
`setup` со входом, успешная ветка `update`, автозапуск на macOS и Linux —
всё это в `docs/ACCEPTANCE.md`.

```
setup          всё после установки пакета: chromium, вход, регистрация, doctor
login          вход в подписку силами демона
status         демон, сессия, версия, каталог состояния — коротко
doctor         полная диагностика; на каждый красный пункт — точная команда
start · stop · restart · logs
register · unregister      Claude Desktop и Claude Code, без абсолютных путей
autostart on · off · status
update         обновить пакет, перезапустить демона, doctor
uninstall      снять всё поставленное; профиль — только с --purge
migrate ПУТЬ   перенести профиль из старой установки (копия, оригинал цел)
call МЕТОД k=v прямой вызов в обход MCP — для отладки
```

Кириллических команд прежнего пульта нет: команда одна, справка по-русски.
Каждая печатает, что сделала, и завершается ненулевым кодом, если не сделала.

## 8. Тестируемость

**Состояние: делается шагом 5.** Ниже — устройство, закреплённое решением 17.

Транспорт выносится в один инъецируемый объект:

```
Transport.fetch(method, url, form) -> (status, ok, text)

реальный  — Playwright внутри демона
тестовый  — фейк, отдающий записанные или синтетические тела
```

`GarantClient` принимает транспорт в конструкторе. Это подмена транспорта,
а не «мок половины клиента»: граница проходит по одному методу, ниже которого
нет ничего, кроме сети. Решение 17.

Образцы двух родов и лежат по-разному:

* **записи владельца** — флаг `GARANT_RECORD=1` заставляет реальный транспорт
  писать сырые тела в `<состояние>/recordings/`. Каталог закрыт `.gitignore`.
  Тексты актов в репозиторий не попадают никогда; у клонировавшего тесты на
  записях пропускаются с причиной;
* **синтетика** — публично, в `tests/fixtures/`, и только на тот слой, форму
  которого задаёт `endpoints.json`: `capture`, `item_map`, порядок шагов
  практики, `status_map`. В каждом файле помечено происхождение.

Ни один офлайн-вариант не ловит смену API «Гаранта». Это отдельный риск,
и закрывает его только живой прогон.

## 9. Что этап не меняет

Девять ограничений `CLAUDE.md` в силе целиком. Отдельно, потому что их
пытаются «упростить» чаще прочего:

* профиль — постоянный каталог, не `storage_state.json` (решение 1);
* демон единолично владеет профилем (решение 2);
* демон слушает только `127.0.0.1`, хост в конфигурацию не выносится
  (решение 5);
* опознание демона по `/health` до отправки токена, без кэширования
  (решение 9);
* период keepalive зажат в 15…240 с (решение 7);
* `ALLOWED` не расширяется — кроме `login` как внутренней операции демона;
* карта эндпоинтов публикуется (решение 10);
* лицензия Apache-2.0 и `NOTICE` (решение 13);
* модель продукта: доступ даёт собственная подписка пользователя, ничего
  не проксируется, хостинга нет.
