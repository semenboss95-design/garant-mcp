# Журнал решений

Здесь лежат решения, которые неочевидны из кода и которые кто-нибудь однажды
попытается «упростить». Формат один: **решение — почему — что было бы иначе**.

Записывать сюда стоит то, у чего есть цена ошибки. Выбор имени переменной сюда
не идёт.

---

## 1. Профиль браузера — постоянный каталог, а не `storage_state.json`

**Решение.** Сессия «Гаранта» живёт в каталоге профиля Chromium
(`chrome_profile`), который Playwright открывает как persistent context.
`storage_state.json` для авторизации не используется.

**Почему.** «Гарант» авторизуется через OAuth (ORY_HYDRA). Часть токенов
хранится в `sessionStorage`, а `storage_state` его не сохраняет — только cookie
и `localStorage`.

**Что было бы иначе.** Переход на `storage_state.json` выглядит как упрощение
(один файл вместо каталога на сотни мегабайт) и ломает вход: после
восстановления состояния часть OAuth-контекста отсутствует, запросы получают
`Unauthorized`. Диагностируется плохо — выглядит как «истекла сессия».

---

## 2. Демон единолично владеет профилем

**Решение.** Браузер держит один процесс — `daemon.py`. `server.py` не трогает
Playwright вообще, а ходит к демону по HTTP на `127.0.0.1`.

**Почему.** Один каталог профиля Chromium может быть открыт ровно одним
процессом. Второй получает блокировку либо портит профиль.

**Что было бы иначе.** Если бы MCP-сервер поднимал браузер сам, то два
одновременных MCP-клиента (Claude Code и Claude Desktop) дали бы два процесса на
один профиль. По той же причине `auth_login.py` и сервер нельзя запускать
одновременно.

---

## 3. `STATE` по умолчанию — пользовательский каталог данных ОС, а не папка кода

**Решение.** Рантайм (`daemon_token`, `daemon_port`, `chrome_profile`, `logs/`,
`cache/`) по умолчанию живёт в `platformdirs.user_data_dir("garant-mcp")`.
Состояние рядом с кодом — явный опт-ин через `GARANT_HOME`.

**Почему.** Установка через `pip`/`uvx` кладёт код в `site-packages` или
в эфемерный кэш uv: каталог доступен только на чтение либо стирается между
запусками. Писать рантайм рядом с кодом там невозможно.

**Что было бы иначе.** При умолчании «рядом с кодом» репозиторий работает только
как git-clone. Под `pip`/`uvx` демон падает на записи токена, а клиент показывает
невнятное «сервер не запустился».

**Оговорка.** У уже существующей установки `chrome_profile` и `daemon_token`
лежат рядом с кодом. Поэтому: если `GARANT_HOME` не задана, но в каталоге кода
уже есть установка — она считается портативной, `STATE` берётся оттуда, ничего
не переносится автоматически. Иначе смена умолчания заставила бы входить заново.

**Оговорка отменена решением 14 (05.09.2026).** Основное решение — состояние
в каталоге данных ОС — остаётся в силе и становится единственным; эвристика
«следы рядом с кодом делают установку портативной» удаляется вместе с самим
понятием портативного режима. Причина: она угадывала намерение по следам
и угадывала неверно ровно тогда, когда копий кода становилось больше одной.
Перенос профиля из старой установки делает `garant migrate` — явной командой,
а не догадкой.

## 4. Выбор порта — bind-then-write, а не probe-then-bind

**Решение.** Демон биндится сразу и ловит `OSError`, повторяя на следующем порту
в ограниченном диапазоне. Занятость заранее не проверяется. Фактический порт
и PID пишутся в `STATE/daemon_port` **после** успешного бинда, атомарно
(временный файл → `os.replace`).

**Почему.** Проверка занятости перед биндом — классический TOCTOU: между
проверкой и биндом порт заберёт другой процесс.

**Что было бы иначе.** Демон изредка падал бы «уже занят» на порту, который
секунду назад был свободен. Воспроизводится плохо, чинится долго.

**Следствие.** Клиент, прежде чем послать `X-Token`, обязан сходить на
`GET /health` и убедиться, что на порту наш демон. Файл `daemon_port` может быть
протухшим — демон умер, порт занял кто-то посторонний — и токен ушёл бы
случайному локальному слушателю.

## 5. Демон слушает только `127.0.0.1` и настройки хоста не имеет

**Решение.** Адрес прослушивания зашит. В конфигурацию не выносится.

**Почему.** Это граница безопасности, а не параметр. Демон держит
авторизованную сессию платной подписки и белый список `ALLOWED` намеренно узок:
браузер наружу не отдаётся.

**Что было бы иначе.** Настраиваемый хост однажды окажется выставлен в `0.0.0.0`
«чтобы проверить с другой машины» — и подписка станет доступна всей сети.
Токен от этого не спасает: он лежит в файле рядом.

## 6. Ужесточение pre-commit после приёмки этапа 01 — ИСПОЛНЕНО 04.09.2026

**Решение.** Предупреждающий уровень хука (следы прежней раскладки, буква
диска в тексте, упоминание исходного вольта — точные образцы выписаны
в `hooks/pre-commit`) поднят до отказа. Уровень предупреждения в хуке больше
не используется вовсе: функция `warn` удалена, осталась одна `deny`.

**Почему нельзя было раньше.** Эти литералы были в коде: 19 попаданий в 9
файлах. Строгий уровень заблокировал бы первый же коммит кода, который ещё не
дошёл до своей починки. Хук, отвергающий всё, отключат в первый же день — и
защиты не останется вовсе.

**Почему сделано сейчас.** Этап 01 принят, литералов не осталось.
Предупреждение перестало нести информацию и стало шумом, который перестают
читать. Отказ возвращает ему смысл: с этого момента появление такого
литерала — регрессия, а не наследство.

### Что изменилось в файле

Четыре правила переведены из `warn` в `deny`: каталог прежней раскладки,
путь внутрь venv, буква диска в тексте, название исходного вольта. Тексты
правил переписаны: они больше не ссылаются на «этап 01», который закончился,
а называют причину — почему этого литерала не должно быть у постороннего.

Сами образцы здесь не выписаны, и это не небрежность. Точные образцы живут
в `hooks/pre-commit` — там единственное место, где их правят; выписанные
вторым списком, они разошлись бы с первым молча. По этой же причине запись
не потребовала себе освобождения в хуке: журнал объясняет решения, а не
ищет литералы, и назвать правило можно, не приводя его образца. Проверка
на себе: этот файл проходит хук наравне с остальными.

**Исключения — поимённые**, в функции `exempt`. Их ровно три, и все три
одного рода: файл, который ИЩЕТ литерал, обязан его содержать.

* `scripts/acceptance.ps1` — по всем четырём правилам. Это ворота, они
  ищут ровно эти образцы. Та же причина, по которой хук пропускает сам себя.
* `scripts/_common.ps1` и `.mcp.json.example` — только по venv. Там venv
  не требование, а первый из четырёх кандидатов на интерпретатор и путь,
  который туда пишет `register_global.ps1`.

Исключение узкое, и это проверено: `ОТКАЗЫ 1-4` (структура `storage_state`,
`Set-Cookie`, длинная base64url-строка вне кода, путь рабочей машины)
применяются ко всем без изъятия. Попытка дописать `Set-Cookie` в
`acceptance.ps1` или машинный путь в `_common.ps1` отклоняется; освобождение
по venv не распространяется на остальные три правила.

### Ложное срабатывание, вскрывшееся при проверке

Образец буквы диска ловил обычный питоновский исходник: строка, кончающаяся
экранированным переводом строки перед закрывающей кавычкой, выглядела для
него как буква диска с разделителем. Пять попаданий в `tests/test_port.py`,
все на пустом месте. Для предупреждения это был шум; для отказа это
блокировка коммита без причины — то, после чего хук отключают.

Отсечено по кавычке следом, а не запретом самих букв `n`, `r`, `t`:
у настоящего пути после них идёт продолжение имени, у экранирования — конец
литерала. Запрет по букве отбросил бы вместе с ложными и настоящие пути,
то есть чинил бы ложное срабатывание ценой пропуска.

Тот же разбор теперь и в `acceptance.ps1`. Два детектора одного правила
обязаны понимать его одинаково: разойдясь, они дают худший из возможных
результатов — коммит проходит, а ворота падают, или наоборот.

**Проверено в обе стороны.** Каждое из четырёх правил отклоняет подложенный
литерал и называет себя; обычный коммит проходит молча; восемь похожих, но
законных строк (экранированный перевод строки, `https://`, `file:///`,
двоеточие в обычном тексте, название меры пресечения как юридический термин,
а не как имя вольта) проходят;
три освобождённых файла коммитятся; секрет в форме `daemon_token` в файле
без расширения по-прежнему отклоняется.

**Что нарочно не тронуто.** Правило про длинную base64url-строку по-прежнему
не применяется к файлам, которые считаются кодом (`is_code`), включая `.txt`.
Настоящий `daemon_token` расширения не имеет и под правило попадает — это
проверено. Расширять правило на `.txt` значило бы ловить хеши и разделители
в человеческом тексте; решение осталось таким, каким принято на этапе 00.

### Дополнено 06.09.2026 (этап 02): образцы машины уехали за пределы индекса

Запись выше говорит: «точные образцы живут в `hooks/pre-commit` — там
единственное место, где их правят». Для образцов **прежней раскладки и
прежнего хранилища это больше не так**, и вот почему.

Хук — публичный файл. Держа в себе имя пользователя рабочей машины как образец
поиска, он публиковал ровно то, что запрещает публиковать. Проверка «история
чиста по ОТКАЗАМ 1-4» была верна ровно потому, что детектор не смотрел на себя:
у него стояло поимённое исключение.

Стало так:

* **имя пользователя** берётся у машины, а не пишется литералом. Источников
  четыре, и это не перестраховка: имя учётной записи и имя каталога профиля
  на одной и той же машине **различаются**, а в путях встречается второе.
  «Первый непустой источник» проверял бы имя, которого в путях нет, и молчал
  бы об этом. Негодные имена (короткие, родовые, с посторонними символами)
  отбрасываются, и каждое — отдельной строкой в stderr: выключенная проверка,
  о которой никто не знает, хуже отсутствующей;
* **литералы прежней раскладки и прежнего хранилища** живут в необязательном
  `.git/garant-secrets`, по одному образцу в строке. Файл вне индекса и в клон
  не попадает. Его отсутствие — не дыра, а правильное поведение: там следы
  **чужой** машины, которых у клонировавшего нет и быть не должно. Формат —
  `hooks/README.md`;
* **исключение «хук пропускает сам себя» снято.** После выноса литералов
  самосовпадающим остался один образец — ключи `cookies` и `origins` в
  ОТКАЗЕ 1; он переписан так, чтобы не совпадать с собственным текстом.
  Отсюда правило для следующего, оно записано в шапке хука: **образец
  пишется так, чтобы не находить сам себя.** Иначе хук отвергает собственную
  правку, и его снова придётся освобождать поимённо — то есть возвращаться
  к состоянию, из-за которого утечка и дожила до аудита.

**Судьба трёх освобождений в `exempt()`.** Все три выданы файлам из
`scripts/`, которые удаляются на шагах 3-4 (решение 18). Они умирают вместе
со своими файлами, и это обязанность того, кто файл удаляет. Освобождение,
пережившее свой файл, — это тихо выключенное правило: оно продолжает
действовать на путь, по которому завтра может лечь что угодно.

**Почему хук молчит об отсутствии `.git/garant-secrets`, но кричит о ненайденном
имени пользователя.** Асимметрия намеренная, и решена она здесь, потому что
`release-gate` справедливо назвал её расхождением. Ненайденное имя пользователя —
**аномалия**: имя есть на любой машине, и если его не удалось получить, что-то
не так со средой, а проверка при этом выключилась. Отсутствие
`.git/garant-secrets` — **норма**: у клонировавшего этого файла нет и быть
не должно. Печатать строку при каждом коммите у каждого пользователя ради
состояния, которое для него правильное, значит приучить не читать stderr хука —
а тогда обесценится и сообщение про имя. Цена решения названа прямо: на машине,
где следы прежней раскладки реально есть, эта проверка выключена молча, и держит
её наличие файла, то есть дисциплина владельца, а не механизм.

## 7. Период keepalive — настройка с потолком, а не свободный параметр

**Решение.** `GARANT_KEEPALIVE_SEC` и `daemon.keepalive_sec` зажимаются
в 15…240 секунд. Выход за предел не считается ошибкой: применяется граница,
а демон пишет в лог, что было запрошено и что применено.

**Почему.** Ограничение 4 из `CLAUDE.md`: keepalive `POST /server/keepalive`
обязателен, cookie `_keepalive_` живёт единицы минут. Период за этой границей —
не «настройка пореже», а выключение продления сессии. Настройка, способная
тихо сломать рабочую вещь, настройкой быть не должна.

Верхняя граница — про Гарант, нижняя нет: 15 секунд стоят внизу из приличия,
пинг раз в секунду это лишний трафик к чужому серверу, а не защита от поломки.

**Что было бы иначе.** `GARANT_KEEPALIVE_SEC=3600` выглядит как разумная
экономия и молча роняет подписку посреди работы. Пользователь видит не
«истёк keepalive», а «Гарант перестал отвечать», и лечится это ручным
повторным входом в браузере — то есть ценой ровно того, что ограничение 4
и защищает.

**Что нарочно не сделано.** Значение за пределом не роняет демон с ошибкой.
Упасть на старте из-за настройки, без которой контур прекрасно работает
на умолчании, — хуже, чем применить границу и сказать об этом в логе.

**Оговорка.** `daemon.keepalive_sec` и `keepalive.interval_sec` в
`endpoints.json` — разные вещи, и совпадение их значений (120) случайно.
Первое — период таймера демона, второе — троттл попутного продления внутри
клиента. Зажим касается только первого: демон пингует с `force=True`
и троттл обходит.

## 8. Файловый мост выключен по умолчанию, его единственный клиент удалён

**Решение.** `daemon.py` создаёт `bridge/requests`, `bridge/responses` и
сканирует очередь только при `config.BRIDGE` (`GARANT_BRIDGE=1` либо
`daemon.bridge` в `endpoints.json`). Код моста сохранён целиком: выключается
поведение, а не возможность. `reference/garant_bridge.py` — единственный
клиент моста — удалён.

**Почему мост выключен.** Мост — второй вход в демона, и вход **без токена**:
кто может писать в каталог состояния, тот исполняет любой метод из `ALLOWED`.
HTTP-контур опознаёт вызывающего токеном, мост не опознаёт никак — он и не
может, файл не предъявляет удостоверения. Это оправдано ровно в одной среде:
песочница Cowork живёт на другой ОС, со своим localhost, но с общей файловой
системой, и постучаться на `127.0.0.1` нашей машины не в состоянии. У всех
остальных мост открыт впустую. Пустые `bridge/requests` и `bridge/responses`
в каталоге состояния — не «лишние папки», а приглашение положить туда файл.

**Почему клиент удалён, а не помечен комментарием.** Он вычислял расположение
моста сам — своей функцией `_garant_home()`, по `GARANT_HOME` или по соседству
с кодом. Это второй источник истины о расположении, ровно тот, от которого
избавляется этап 01, и после `paths.py` он уже неверен: клиент ищет `bridge/`
рядом с кодом, а демон создаёт его в `STATE`, который по умолчанию уехал в
каталог данных ОС. Комментарий «требует `GARANT_BRIDGE=1`» в шапке был бы
правдой про одну поломку и умолчанием про вторую: файл не заработал бы и с
включённым мостом.

**Что этим не потеряно.** Протокол моста тривиален и целиком описан в
`daemon._bridge_scan`: в `STATE/bridge/requests` кладётся `<id>.json` с телом
`{"метод": ..., "параметры": {...}}` — атомарно, через запись во временный
файл и `replace`, иначе демон подхватит полуфайл; ответ появляется в
`STATE/bridge/responses/<id>.json` и содержит либо `результат`, либо `ошибка`.
Клиент к такому протоколу пишется за вечер, и писать его надо под ту среду,
которой он понадобился, — а старый был написан под расположение, которого
больше нет. История файла остаётся в git.

## 9. Опознание демона не кэшируется: /health перед каждым вызовом

**Решение.** `daemon_client._убедиться_что_наш()` ходит на `GET /health`
перед каждым обращением к демону. Опознание не кэшируется ни на процесс,
ни на время. Вариант «опознать один раз, переопознать после неудачи»
рассмотрен и отклонён.

**Почему.** Кэш — это утверждение о прошлом. «Полчаса назад на этом порту
был наш демон» не значит «сейчас там наш демон», а решение, которое
принимается по этому утверждению, необратимо: токен от живой подписки
уходит тому, кто ответил. Отозвать его нельзя — можно только перезапустить
демона, узнав об утечке.

Промежуток между двумя вызовами — не теоретический. Сессия MCP-клиента живёт
часами; демон за это время может умереть, а порт занять любая локальная
программа. Больше того, демона убивает сам пульт — команды `стоп`, `окно`
и `скрыть` именно этим и заняты. Ровно на этот случай проверка и появилась.

**Почему переопознание после неудачи не спасает.** Неудача наступает не там,
где её ждут. Посторонний на порту не обязан отвечать ошибкой: он отвечает
как умеет — двумястами, редиректом, чем угодно, — а токен к этому моменту
уже ушёл в заголовке запроса. Переопознание случилось бы после утечки,
а не вместо неё.

**Чего это стоит.** Замерено на живом демоне: медиана 15 мс, максимум 26 мс
на опознание (петля 127.0.0.1, `BaseHTTPRequestHandler` без keep-alive).
Вызов к «Гаранту» идёт через браузер и занимает секунды — накладные меньше
процента. Платить проценту за свойство «токен не уходит неопознанному»
выгодно; спорить об этом стоило бы, если бы речь шла о разах.

**Что было бы иначе.** Кэш, привязанный к паре порт+PID, потребовал бы
проверять, жив ли процесс, — то есть того же обращения к ОС и своей гонки
между проверкой и отправкой. Выигрыш исчезает, свойство остаётся под
вопросом.

## 10. `endpoints.json` публикуется

**Решение.** Карта эндпоинтов остаётся в публичном репозитории. Принято
владельцем 05.09.2026.

**Почему.** Без неё репозиторий неработоспособен: `garant_client.py` целиком
построен на ней — шаги запросов, `item_map`, `response_map` читаются оттуда,
а не зашиты в код. Публиковать клиент без карты значит публиковать половину,
которая не запускается.

Содержимого базы карта не содержит. В ней адреса, имена полей и порядок
вызовов — то, что видит в своём браузере любой подписчик, открыв инструменты
разработчика. Доступ по-прежнему даёт собственная подписка пользователя.

**Что это меняет для работы.** `endpoints.json` — публичный файл и подпадает
под все правила публичных файлов: ни путей машины, ни следов раскладки,
ни висячих ссылок. Правки в него проходят те же ворота, что код.

## 11. Имя репозитория — `garant-mcp`, первый экран про подписку

**Решение.** Вариант А из `docs/LAUNCH.md`: один репозиторий, имя по «Гаранту»,
конвейер реверса в `tools/` лежит внутри как деталь реализации. Принято
владельцем 05.09.2026.

**Почему.** Продукт готов приносить пользу ровно одной аудитории — тем, у кого
уже есть подписка «Гаранта» и MCP-клиент. Имя по методу (`traffic-to-mcp`)
расширяет аудиторию, но хуже находится теми единственными, кому продукт
сегодня полезен. Два репозитория для одного человека дороже в сопровождении,
чем стоит выигрыш.

**Что это задаёт README, когда до него дойдёт дело.** Первый экран отвечает
на вопрос читателя «могу ли я поставить это в документ», а не «как устроен
транспорт». Отличие от «спросить у ИИ про закон» — не удобство, а
**проверяемость**: `provenance` и редакция на дату существуют потому, что цена
ошибки здесь не «я неверно понял», а документ, поданный со ссылкой на
недействующую норму.

Демон, скрипты и конвейер на первом экране не упоминаются вовсе — это обвязка,
ей место ниже. Примеры не сводятся к уголовному процессу: контур работает
с любой отраслью, а УПК — след происхождения; один пример оттуда уместен,
три подряд сужают продукт до одной практики.

**Что решением не закрыто.** Когда публиковать — до тестов клиента или после.
Это развилка, а не план; см. `docs/TEAM.md`, §7.

## 12. ОТКРЫТЫЙ ВОПРОС: текст статьи в редакции на дату

**Не решение, а вопрос к владельцу.** Записан 05.09.2026, решать после живой
приёмки.

**В чём дело.** `garant_revision_on_date` отвечает на вопрос «какая редакция
действовала на дату» и возвращает запись о редакции: название, статус, период
действия, изменяющий акт, `id_редакции`. **Текста нормы в ответе нет.**

Тот, кому нужен текст, идёт в `garant_article` — а тот параметра редакции не
принимает и собирает `provenance` по действующей. Получается цитата из
сегодняшней редакции рядом с утверждением, что действовала другая. Это ровно
та ошибка, против которой инструмент написан, и до 05.09.2026 описание
инструмента её не только не предотвращало, а провоцировало: оно называло себя
обязательным при цитировании прошлого события, умалчивая, что текста не даёт.

**Что сделано сейчас (и только это).** Описания в `server.py` и
`garant_client.py` приведены к правде: сказано, что возвращается редакция
и её реквизиты, а не текст; сказано, что прямого способа взять текст той
редакции нет; сказано, что ставить рядом текст из `article` и вывод этого
инструмента нельзя. Код не менялся.

**Непроверенная возможность.** `revisions()` отдаёт `id_редакции` — это
`documentId` самой редакции из `/redactions/list`. Он выглядит как мост:
если `article()` принимает его как `doc_id`, текст нужной редакции достаётся
существующими средствами. **Проверить без живой подписки нельзя.** Поле
сегодня не используется нигде в коде — оно возвращается и пропадает.

Проверяется одним запросом на живой приёмке: взять `id_редакции` недействующей
редакции и передать его в `garant_article`. Ответ решает вопрос.

**Что решает владелец, а не рой.** Если мост работает — нужен ли параметр
редакции в `garant_article` и `garant_document`, и как тогда выглядит
`provenance` (редакция запрошенная, а не действующая). Если не работает —
остаётся ли инструмент как есть с честным описанием, или ищется другой путь.
Это меняет форму ответа двух главных инструментов, поэтому решение не
принимается на ходу.

## 13. Лицензия — Apache-2.0

**Решение.** Apache License 2.0. Правообладатель — Oleksandr Diachenko,
год 2026. Принято владельцем 05.09.2026. Файлы: `LICENSE` и `NOTICE`.

**Почему не MIT.** Четыре довода, и три из них к этому проекту относятся
конкретно, а не вообще.

**Товарные знаки — § 6.** Apache-2.0 прямо оговаривает, что лицензия **не даёт
прав на товарные знаки** правообладателя и не разрешает использовать его имя.
Здесь это не абстракция: в имени репозитория стоит чужой знак — «Гарант», —
и продукт целиком построен вокруг чужого сервиса. Явная оговорка о том, что
лицензия на код никаких прав на знак не передаёт и передать не может, снимает
двусмысленность, которой в MIT просто нет текста.

**Патенты — § 3.** Apache-2.0 даёт явную патентную лицензию от участников
и отзывает её у того, кто подаст патентный иск против проекта. MIT о патентах
молчит: права даются на «Software», патентные притязания остаются открытым
вопросом. Для `tools/` это существеннее обычного — там описан метод
восстановления клиента к чужому API, и это как раз область, где патентные
претензии встречаются.

**Отметка об изменениях — § 4(b).** Форк обязан указать, что файлы изменены.
Продукт заявляет проверяемость нормы; форк, тихо ослабивший `provenance` или
убравший предупреждения о неполноте текста, выглядел бы как оригинал. MIT
такого требования не содержит.

**Отказ от гарантий — §§ 7-8.** Оба отказывают, Apache-2.0 — подробнее
и отдельными разделами. Для инструмента, чей выход идёт в процессуальный
документ, это не украшение.

**Что было бы иначе при MIT.** Короче и знакомее: MIT читают до конца, и он
не вызывает вопросов у юриста компании-пользователя. Apache-2.0 иногда требует
согласования. Взамен исчезли бы все четыре пункта выше — в первую очередь
оговорка о знаке и патентная защита. Для репозитория, названного чужим знаком,
эта потеря дороже удобства.

**NOTICE — не издержка формата, а место для заявления.** Apache-2.0 требует
сохранять `NOTICE` при распространении, в том числе в форках. Туда вынесено
то, что сейчас живёт только в `README.md` и при форке исчезает первым: проект
не аффилирован с «Гарантом», не содержит содержимого базы и не проксирует
чужой доступ. README форк перепишет под себя за минуту; `NOTICE` он обязан
донести.

### Чего лицензия не делает — и это отдельный вопрос

**Ни одна лицензия не влияет на главный риск проекта — отношения
с «Гарантом».** Лицензия описывает права на **наш код**: кто может его брать,
изменять и распространять. Она ничего не говорит и не может сказать о том,
допустимо ли автоматизированное обращение к чужому сервису с точки зрения его
правил, и не создаёт никаких прав в отношении «Гаранта».

Смешивать эти два вопроса нельзя. «У нас Apache-2.0» не является ответом на
вопрос «а можно ли так делать»; выбор лицензии этот вопрос не приближает
и не отдаляет. Он остаётся открытым и решается не лицензией.

## 14. Установка — Python-пакет и один каталог состояния

**Решение.** `garant-mcp` ставится как Python-пакет (`uv tool install`, при
отсутствии `uv` — `pipx`) и даёт три исполняемых файла в `PATH`: `garant`,
`garant-mcp`, `garant-daemon`. Состояние живёт в
`platformdirs.user_data_dir("garant-mcp")` и больше нигде. `GARANT_HOME`
переопределяет **только** этот каталог. Эвристика «состояние рядом с кодом,
если рядом с кодом найдены следы установки» удаляется вместе с понятием
«портативный режим». Принято 05.09.2026, этап 02.

**Почему.** До этого решения на активную установку указывали девять
независимых указателей: две пользовательские переменные окружения, задача
планировщика, ярлык автозагрузки, три вида регистрации у MCP-клиентов,
конфигурация плагина и каталог состояния. Их писали разные скрипты, ни один
не показывал их вместе, и никто не сверял. Хуже того, `GARANT_HOME` означала
разное для разных участников: каталог состояния для `paths.py`, каталог кода
для установщика и для плагина. Совпадало это ровно тогда, когда состояние
лежало рядом с кодом, — то есть в единственной раскладке, от которой решение 3
и уходило.

Отсюда наблюдаемый симптом: правки идут в одну копию кода, инструменты
работают из другой, а `статус` отвечает «демон работает» у обеих. Человек
видит не «две установки», а «правки не доходят».

Три указателя вместо девяти: чем исполнять (файлы в `PATH`), где состояние
(каталог данных ОС), кто запускает сервер (запись `{"command":
"garant-mcp"}` в конфигурации клиента). Ни один не содержит абсолютного пути,
поэтому обновление не требует переписывать регистрации, а регистрация
не устаревает от переезда кода.

**Что было бы иначе.** Вариант «репозиторий = установка» дешевле на один
каталог и делает инструмент, которым владелец подаёт документы, зависимым от
того, что агент дописал в дереве минуту назад. Вариант «установка — второй
клон репозитория» это чинит, но оставляет двойную семантику `GARANT_HOME`
и требует, чтобы человек понимал разницу между репозиторием и установкой.
Пакет закрывает вопрос структурно и ценой одного переезда: профиль копируется
`garant migrate` при остановленном демоне либо выполняется повторный вход.

**Следствие для `endpoints.json`.** Пакетный файл обновлением затирается,
поэтому пользовательская правка живёт отдельно — в
`<состояние>/endpoints.local.json`, который сливается поверх пакетного. Иначе
«обновить» означало бы «потерять свою настройку молча».

## 15. Вход в подписку выполняет демон

**Решение.** `garant login` посылает демону `POST /login`. Демон закрывает
headless-контекст, открывает **видимое** окно на своём же профиле, ждёт
входа, закрывает окно и возвращается в headless. Отдельного процесса входа
не существует; `auth_login.py` удаляется. `login` добавляется в `ALLOWED`
как внутренняя операция, доступная только под токеном и только с петли.
Принято 05.09.2026, этап 02.

**Почему.** Ограничение 2: один профиль — один процесс. Прежний вход это
ограничение нарушал по устройству: `daemon_client.login()` печатал «демон
будет остановлен», посылал `/restart` — а `/restart` перезапускает браузерный
контекст, но не процесс, — и тут же запускал вторым процессом `auth_login.py`
на тот же профиль. Демон при этом продолжал работать и по таймеру снова
открывал профиль. Исход зависел от того, кто успел первым.

Единственный, кто вправе открыть этот профиль, — тот, кто им владеет. Значит,
окно входа открывает демон.

**Что было бы иначе.** Оставить как есть значит держать в главной процедуре
продукта состояние, которое сам код называет невозможным, и текст, который
описывает не то, что происходит. Вариант «останавливать демона на время
входа» честнее прежнего, но требует, чтобы кто-то поднял его обратно, —
и на время входа исчезает keepalive, то есть процедура восстановления сессии
сама её и роняет.

**Цена.** `ALLOWED` расширяется — впервые с момента появления списка. Это
осознанно и узко: `login` не отдаёт браузер наружу, он открывает окно
человеку за той же машиной, и снаружи петли к нему не обратиться.

## 16. Отпечаток браузера снимается с машины, а не приезжает в клоне

**Решение.** UA, локаль и часовой пояс берутся при первом входе: UA — у
настоящего chromium этой машины (с заменой `HeadlessChrome` на `Chrome`),
локаль и пояс — у ОС, окно — 1440×900. Значения записываются в
`<состояние>/fingerprint.json`; и вход, и работа читают этот файл. Пока файл
существует, значения не меняются. Из `endpoints.json` секция
`browser_profile` теряет значения, остаётся имя каталога профиля. Принято
05.09.2026, этап 02.

**Почему.** Ограничение 3 требует, чтобы отпечаток окна входа и рабочего
контекста **совпадал**, — оно не требует, чтобы он был одинаков у всех
установок мира. А именно это и происходило: значения сняты с машины автора,
лежат в публичном файле и уезжают в каждый клон. Следствий два, и оба
неприятные. Первое: все установки инструмента предъявляют сервису один
опознаваемый отпечаток, и сессия автора среди них. Второе: `timezone_id`
раскрывает регион автора — в публичном файле, вместе со второй независимой
подсказкой того же региона.

**Почему файл, а не чтение ОС каждый раз.** Пояс ОС меняется — поездкой,
переводом часов, сменой настройки. Отпечаток, меняющийся вслед за ним, даёт
`Unauthorized` на живой сессии, и выглядит это как «Гарант сломался».
Зафиксированный файл сохраняет ровно то свойство, которого требует
ограничение 3: совпадение входа и работы. `garant doctor` показывает
расхождение с ОС как **предупреждение** — знать полезно, ломать нельзя.

**Что было бы иначе.** Нейтральное значение в репозитории (скажем, `UTC`)
убирает регион, но сохраняет общий отпечаток на все клоны и добавляет третье
состояние: значение, не совпадающее ни с чьей машиной. Удаление ключей без
файла означало бы, что Playwright берёт настройки ОС в обоих процессах —
это работает, пока ОС не сменила пояс между входом и работой.

**Цена.** Владельцу — один повторный вход после перехода на файл, если
снятый с машины UA разойдётся с прежним. Старый профиль до этого момента
не удаляется.

## 17. Транспорт — точка подмены; тесты клиента пишутся через неё

**Решение.** Весь сетевой вызов клиента уходит в один инъецируемый объект
`Transport.fetch(method, url, form) -> (status, ok, text)`. Реальный транспорт
использует Playwright внутри демона; тестовый отдаёт записанные или
синтетические тела. `GarantClient` принимает транспорт в конструкторе. Такая
подмена **не считается** «моком половины клиента» по смыслу
`.claude/rules/tests.md` и `.claude/agents/test-author.md`; оба файла
правятся. Принято 05.09.2026, этап 02.

**Почему.** Клиент не покрыт ни одним тестом на разбор ответа, и это модуль,
который формирует ответ пользователю. Причина не в лени:
правила запрещали подмену, не назвав границы, и наряд на тесты по своему же
протоколу не мог начаться без решения.

Граница выбрана по свойству, а не по удобству: ниже `Transport.fetch` нет
ничего, кроме сети. Всё, что выше, — сборка URL, кодирование формы, повтор
после 401/403, разбор пустого тела, `_dig` с запасными путями, порядок шагов
практики, вырезка статьи, `provenance` — исполняется в тесте целиком.
Подмена, проходящая выше этой границы (например, самого `_fetch`), уводила бы
из-под проверки повтор и разбор — то есть ровно то, что ломается.

**Об образцах.** Два рода и лежат по-разному. Записи владельца — флаг
`GARANT_RECORD=1`, сырые тела в `<состояние>/recordings/`, каталог закрыт
`.gitignore`; тексты актов в репозиторий не попадают никогда, у клонировавшего
такие тесты пропускаются с названной причиной. Синтетика — публично, и только
на слой, форму которого задаёт `endpoints.json`; происхождение помечено
в каждом файле. Образец «по карте» там, где клиент читает мимо карты,
образцом по карте не является — такие места правятся, а не обкладываются
тестами, повторяющими реализацию.

**Что было бы иначе.** Без решения остаётся сегодняшнее: любая правка клиента
идёт без сети проверок, а молчаливую поломку первым видит пользователь
в момент подачи документа.

**Чего это не даёт.** Ни один офлайн-вариант не ловит смену API «Гаранта».
Это дрейф контракта, другой риск, и закрывается он только живым прогоном.

## 18. Пульт на PowerShell удаляется; управление — команда `garant`

**Решение.** `garant.ps1`, `_common.ps1`, `SETUP_GARANT.ps1`,
`install_daemon.ps1`, `install_startup_shortcut.ps1`, `register_global.ps1`
удаляются. Их работу выполняет `garant` — команда пакета на Python.
`acceptance.ps1` заменяется на `garant doctor` плюс `pytest` плюс процедуру
живой приёмки в `docs/ACCEPTANCE.md` (написан 06.09.2026). От PowerShell
остаётся один файл —
`install.ps1`, установщик; рядом с ним `install.sh`. Принято 05.09.2026,
этап 02.

**Почему.** Пульт решал три задачи, и все три переехали. Расположение он
спрашивал у `paths.py` и фактический порт — у `daemon_client.py`, то есть был
обёрткой над Python, написанной на втором языке; установку он делал руками,
которые теперь делает пакетный менеджер; регистрацию писал абсолютными
путями, которых в новой раскладке нет вовсе (решение 14).

Второй язык стоит дорого и платит мало. Ловушки PowerShell 5.1 — кодировка
файла, кавычки при вызове нативной программы, кириллица в аргументе, вывод
stderr нативной программы — описаны отдельным правилом и составляют заметную
часть `.claude/rules/powershell.md`; ни одна из них не имеет отношения
к «Гаранту». И главное: пульт работает на одной ОС из трёх, а ядро — на всех.

**Что было бы иначе.** Оставить пульт значит держать два места, где написано
одно и то же, и чинить каждый дефект дважды. Реестр дефектов этапа 01 это
подтверждает: ложные вердикты пульта, «окружение готово» при неимпортируемом
сервере, установщик, не смотрящий на коды возврата, — это не ошибки
исполнителя, а цена второго слоя.

**Что этим не потеряно.** История файлов остаётся в git. Установка на Windows
остаётся однокомандной: `install.ps1` ставит `uv`, ставит пакет и зовёт
`garant setup`.

## 19. Историю сжать до одного коммита перед первым push

**Решение.** Перед первой публикацией `main` сжимается до одного коммита;
полная история сохраняется в локальной ветке, которая не пушится.
Идентичность коммита выбирает владелец. Выполняет владелец; команда готовится
и объясняется заранее. Принято 05.09.2026, этап 02.

**Почему.** История чиста по необратимому — ни структуры `storage_state`,
ни `Set-Cookie`, ни токенов ни в одной ревизии. Но она не чиста по раскладке:
в прошлых ревизиях лежат литералы прежней плоской раскладки, буквы дисков
и название исходного хранилища. Они были там штатно — до 04.09.2026 хук
предупреждал, а не отказывал (решение 6). Публиковать историю, которую
собственный хук сегодня отвергает, — противоречие, и после push оно
неисправимо: объекты остаются доступны по хэшу, и в форках тоже.

**Почему не «оставить, история — доказательство дисциплины».** Не является:
до 04.09 хук был предупреждающим, а осознанный обход следа не оставляет.
Хронология решений живёт в этом файле, с датами, и её сжатие не трогает.

**Что теряется.** Сообщения коммитов исчезают из публичной истории — у
владельца они остаются. Строка решения 8 «история файла остаётся в git»
для постороннего перестаёт быть верной; сказанное там о протоколе моста
остаётся полным и без истории.

**Почему до, а не после.** Сжатие до push бесплатно; после — невозможно.

## 20. Отпечаток переезжает вместе с профилем

**Решение.** `garant migrate` переносит из старой установки не только каталог
профиля браузера, но и `fingerprint.json`. Свой отпечаток новой установки
не удаляется — откладывается рядом с пометкой. Если у источника отпечатка нет
(а у всех установок до решения 16 его нет), `migrate` говорит об этом отдельным
предупреждением и называет симптом заранее. Принято 06.09.2026, этап 02.

**Почему.** Ограничение 3: сессия «Гаранта» привязана к отпечатку браузера,
и требуется **согласованность** окна входа с рабочим контекстом. Сессия
в перенесённом профиле выдана окну со **старым** отпечатком. Оставить новый
значит гарантировать `Unauthorized` на живой сессии — то есть перенос профиля,
затеянный ради сохранения входа, стоил бы ровно того входа, который сохранял.

**Почему свой не удаляется.** Отпечаток снят с этой машины и остаётся верным
описанием её браузера. Если перенос не даст живой сессии и человек войдёт
заново, вернуться к нему надо уметь без повторного снятия.

**Что было бы иначе.** Молчаливое сохранение нового отпечатка даёт отказ,
который читается как «сессия истекла»: человек идёт входить заново — и это
срабатывает, но он так и не узнаёт, что перенос был напрасен. Молчание здесь
дороже ошибки: ошибка чинится один раз, непонимание — каждый раз.

**Чего решение не закрывает.** Работает ли перенесённый профиль на самом деле
и снимает ли перенос отпечатка `Unauthorized` — **непроверено**: требует живой
подписки. Пункт 4 живой приёмки написан так, чтобы этот исход был назван,
а не угадан.

## 21. Границу пункта задаёт оглавление, а не номер в тексте

**Решение.** Конец вырезки статьи или пункта определяется по **оглавлению
акта**: границей считается только тот номер, который оглавление ставит
следующим за найденным узлом того же уровня. Если совпадений этого номера
в тексте несколько, режем по последнему и объявляем конец неподтверждённым;
если ни одного — отдаём остаток и объявляем то же. Дополнительно у «Гаранта»
спрашивается страница следующего узла оглавления: совпадение отбрасывается,
если этой страницы среди загруженных нет. Принято 06.09.2026, этап 02.

**Почему.** Прежнее правило — «граница это первый номер, больший
запрошенного» — работало на статьях и ломалось на пунктах. Пункт 2
с подпунктами «1.; 2.; 3.» обрывался на третьем подпункте: текст возвращался
обрезанным, признак усечения при этом **не выставлялся**, и предупреждения
не было. Уязвим был каждый пункт с малым номером, а не один частный случай,
как утверждал комментарий в коде.

Это худший класс дефекта в этом контуре: всё остальное здесь — усечение
документа, неподтверждённый конец фрагмента — объявляется предупреждением,
и только здесь **цитата уходила обрезанной и выглядела целой**. Юрист,
сверивший её глазами по началу, не увидел бы ничего.

**Почему оглавление, а не эвристика.** Распознать «настоящий заголовок
пункта» среди внутренних перечислений можно было бы регулярным выражением
по редакционной фразеологии. Это тот же класс, что покойное «✓» в судебной
практике: эвристика, выдающая себя за факт. Оглавление — разметка самого
акта, полученная от «Гаранта», а не наша догадка о том, как выглядит текст.

**Цена.** Запрос пункта стоит одного дополнительного сетевого вызова
(`/document/locate` на следующий узел). Связка `/document/info` →
`/document/pages` (ограничение 8) не изменилась; ограничение 9 не затронуто.

**Распространено на статьи (06.09.2026, той же правкой).** Сначала зонд стоял
только в режиме пунктов, а статьи подтверждались слабее — «номер совпал
с названным в оглавлении, и совпадение единственное». `provenance-guard`
назвала конкретный промах: строка вида «Статья 98.» **внутри** тела статьи 97 —
цитата или отсылка с начала строки — давала молчаливый ранний рез. Асимметрия
снята: механизм был уже написан, и оставить его работающим в одном режиме
из двух значило бы держать тот же дефект, только реже.

Цена та же — один лишний вызов на запрос статьи. Возможен и обратный эффект,
и он назван прямо: при отказе эндпоинта фрагмент объявляется неподтверждённым,
и на живой базе это может дать поток предупреждений на исправных вырезках.
Выбор сознательный: ложная тревога исправима читателем, молчаливый рез — нет.
Частоту можно замерить только живьём.

**Что было бы иначе.** Оставить как было значило держать в главном
инструменте цитирования единственное место, где неполнота не объявляется.
Резать «по первому большему номеру» и просто добавить предупреждение —
означало бы, что оно горит почти всегда: перестают читать то предупреждение,
которое общее с усечением документа.

**Чего решение не даёт.** Разбирает ли `_номер_узла` заголовки узлов
на реальных актах — **непроверено**: офлайн видно только «Пункт N» и
«Статья N», а как «Гарант» называет узлы в постановлениях Пленума и в актах
со сложной иерархией, без подписки не выяснить. Если не разберёт, ожидаемый
номер окажется неизвестен и предупреждение станет постоянным — ошибка
в безопасную сторону, но выдача огрубеет. Проверяется на живой приёмке
на постановлении Пленума с нумерованным перечислением внутри пункта.

## 22. Осознанно пропущенный шаг не портит код возврата, но называется вслух

**Решение.** `garant setup --без-входа` завершается кодом 0, если всё
остальное сделано, и **обязательно** печатает громким блоком, что вход
не выполнен, что до входа инструменты не работают и какой командой это
добирается. `garant doctor` при этом различает «демон не отвечает» и «демон
не запускался ни разу»: первое — красное, второе — жёлтое, потому что демона
поднимает сервер при первом же обращении. Принято 06.09.2026, этап 02.

**Почему.** Правило этапа — «ноль только если сделано всё», и вопрос в том,
что считать «всё». Режим `--без-входа` существует ровно затем, чтобы
поставить без входа; возвращая единицу, он рапортует о неудаче там, где
сделал в точности то, о чём просили.

Цена ошибки считается в обе стороны, и обе в этом проекте уже случались:

* **единица на успешной установке** приучает не смотреть на коды возврата.
  Это тот самый механизм, которым обесценился «успех после двух ERROR»:
  человек, дважды получивший тревогу на пустом месте, третью пропустит —
  а она будет настоящей;
* **молчаливый ноль** оставляет установку, которая выглядит законченной
  и не работает. Человек ищет поломку там, где её нет.

Отсюда форма решения: код возврата отвечает на вопрос «сделано ли то, за что
взялись», а текст — на вопрос «чего не хватает». Второе обязательно при любом
коде. **Молчание не является выбором ни при нуле, ни при единице.**

**Симметричное следствие.** Тот же перекос был в другую сторону: `setup`
при неудавшейся регистрации печатал «продолжаю», а десятью строками ниже
заканчивался словами «установка завершена не полностью». Одно событие,
два веса в одном выводе, и человек не понимает, то же это событие или
другое. Вес формулировки приведён к весу итога: на месте сказано, что
инструменты в этом клиенте не появятся и что итог будет ненулевым, пока
не выполнен `garant register`.

**Что было бы иначе.** Разводить эти случаи кодами возврата (скажем, 0, 2 и 1)
выглядит точнее и хуже: код читает не человек, а установщик и будущий CI,
и каждое новое значение — это развилка, которую кто-то однажды не обработает.
Двух значений хватает, если текст честен.

**Чего решение не даёт.** Различитель «демон не запускался» — наличие файла
токена, который демон кладёт при первом запуске. Удалив только его и оставив
прочее состояние, человек получит жёлтый пункт вместо красного. Цена мала
(демон поднимается сам), но случай назван, а не умолчан.

## 23. Растущее число не живёт в постоянном контексте

**Решение.** Число тестов не пишется в `CLAUDE.md`. Там сказано, **что**
покрыто, а сколько — смотрят выводом `pytest`. Правило `docs/TEAM.md` «каждое
число несёт дату замера» остаётся в силе для чисел, которые не меняются
каждым нарядом. Принято 07.09.2026, этап 02.

**Почему.** Число тестов в `CLAUDE.md` протухло **три прогона ворот подряд**:
43 при 169, 169 при 176, и каждый раз его ловили ворота, а не автор. Дата
замера при нём стояла — то есть правило соблюдалось буквально и не помогало
совсем.

Причина не в невнимательности. `CLAUDE.md` — постоянный контекст, он читается
в начале каждой сессии и правится редко; число тестов меняется в каждом
наряде, который пишет тест. Между этими двумя частотами разрыв, и он
закрывается либо правкой при каждом изменении — то есть обещанием, — либо
удалением числа оттуда, где оно не может быть свежим.

Число с датой, разошедшееся с фактом, хуже числа без даты: оно **выглядит
проверенным**. Читатель видит «замер 06.09.2026» и не идёт проверять.

**Что было бы иначе.** Оставить и «просто не забывать» — четвёртый заход
на те же грабли. Завести тест, сверяющий число в документе с выводом
`pytest`, — тавтология: он бы проверял, что мы переписали одну цифру
в другое место, и падал бы у каждого, кто добавил тест.

**Граница.** Решение касается только чисел, растущих сами собой. Числа,
у которых есть цена ошибки и которые не меняются от каждой правки — девять
ограничений, двадцать три решения, восемь ролей, — остаются с датой замера
там, где стоят.

## 24. Уточнение по суду в практике отбирается на клиенте — исключение из ограничения 9

**Решение.** Ограничение 9 («практика требует серверных фильтров, клиентский
отбор по заголовкам не годится») получает **одно** названное исключение:
аргумент `court` инструмента `garant_practice` сужает уже отфильтрованный
сервером список **подстрокой заголовка на стороне клиента**
(`client.py`, `practice()`). Само исключение существовало в коде с этапа 01;
здесь оно оформляется решением с номером, как того требует ограничение 6:
расширение проходит решением, а не молчанием. Принято 07.09.2026, этап 03.

**Почему не серверным фильтром.** Серверного фильтра «суд» в снятом трафике
нет. Цепочка `/list/kind` → `/list/filter` → `/list/page` сужает по **виду
информации** и по **периоду**; орган, вынесший акт, в ней параметром не
является. Узел «Орган» существует в дереве фасетов, но его запрос не снят:
живой базы в среде разработки нет, а снимать трафик может только владелец
на своей подписке. Пока запрос не снят, серверного варианта не существует —
не «он хуже», а его нет.

**Почему тогда вообще есть `court`.** Без него читателю остаётся вручную
глазами перебирать страницу выдачи, то есть делать ровно тот же отбор по
заголовку, только молча и без предупреждения. Инструмент, делающий это
явно и говорящий, чего он не гарантирует, честнее пустого места.

**Чем исключение ограничено — три условия, все выполнены в коде.**

1. Отбор идёт **после** серверных шагов, а не вместо них: `_run_steps`
   базового поиска, затем `kind_step`, затем `date_step`, и только потом
   фильтр по заголовку. Порядок шагов сторожит
   `tests/test_client_практика.py::test_каждый_шаг_несёт_новый_doclist_id`.
2. Отбор идёт по **полной** странице, а не по её началу: потолок в 50 позиций
   снят, иначе акт нужного суда терялся до фильтра по причине, которой не было
   ни в одном предупреждении.
3. Ответ **всегда** несёт `_предупреждение`, где третьей причиной названо:
   уточнение по суду сделано отбором по заголовку на клиенте, акт с иначе
   названным заголовком в выдачу не попадёт, и вывод «у этого суда практики
   нет» из такого ответа **не следует**. Безусловность предупреждения
   сторожит `tests/test_client_практика.py::test_предупреждение_о_неполноте_безусловно`,
   а наличие этой третьей причины —
   `::test_уточнение_по_суду_отбор_на_клиенте_назван_явно`.

**Что было бы иначе.** Убрать `court` до появления серверного фильтра —
внешне чище и на деле хуже: отбор никуда не денется, он переедет к читателю
и потеряет предупреждение. Оставить как есть без решения — оставить
ограничение 9, которое код нарушает открыто и с комментарием: следующий
проверяющий тратит проход на то, чтобы заново установить уже известное.
Ровно это и произошло 07.09.2026 на воротах этапа 03.

**Граница.** Исключение распространяется на `court` и ни на что другое.
Вид информации и период остаются серверными; появление ещё одного
клиентского отбора — новое решение, до кода. Как только запрос по узлу
«Орган» будет снят с живой базы, исключение подлежит отмене: серверный
фильтр отменяет его без отдельного обсуждения.

## 25. `.txt` не считается кодом: правило про токен обязано к нему применяться

**Решение.** Из `is_code()` в `hooks/pre-commit` убран `*.txt`. Правило
«длинная base64url-строка вне кода» теперь применяется и к текстовым файлам.
Остальные расширения списка не тронуты. Принято 07.09.2026, этап 03.

**Почему.** `.txt` был в списке «кода», то есть освобождён от проверки на
токен, — а это ровно то место, куда токен и попадает: перенаправленный вывод
команды, «сохранил на минуту», файл рядом с отладкой. Проверено 07.09.2026:
подложенный в `.txt` длинный литерал хук **пропускал**, тот же литерал в файле
без расширения — отвергал. Цена обратного решения нулевая: `git ls-files
'*.txt'` пуст, ложным срабатываниям сегодня не на чем возникнуть.

**Как нашлось — и почему это важнее самой правки.** Дефект прожил незамеченным
не потому, что хук не проверяли, а потому, что `tests/test_хук_пробы.py`
подкладывает нарушения в файлы **любых расширений, кроме `.txt`**. Проба,
которой нет, — это не «менее полное покрытие», это уверенность на пустом месте:
пробы шли, зелёное получалось, правило не работало. Сторож на этот случай
заказан `test-author` в тот же день, вместе с закреплением самого списка
«кодовых» расширений как ожидания, чтобы его расширение требовало правки
теста, то есть осознанного шага.

**Граница, названная прямо.** `.md` остаётся кодом. Документация репозитория
полна длинных идентификаторов — хэшей коммитов, имён веток, примеров, — и
правило дало бы поток ложных отказов. Следствие: **секрет, положенный
в `.md`, этот хук по данному правилу не увидит.** Прочие правила (структура
`storage_state`, `Set-Cookie`, путь машины, имя пользователя) к `.md`
применяются по-прежнему.

**Что было бы иначе.** Освободить `.txt` «до первого настоящего `.txt`
в репозитории» — то же самое молчаливое исключение, только отложенное:
появившийся файл никто бы не связал с давним послаблением. Отсев по составу
строки (нужны цифры и оба регистра) оставлен как был — токен из одних
строчных и цифр `.txt` пройдёт; граница не сдвигалась ни в одну сторону
и названа здесь, чтобы не считаться закрытой.

## 26. Надстрочный индекс отделяется кареткой; правило отпечатка поднято до `strip_html/2`

**Решение.** Нормализация текста нормы перестала склеивать разметку:
`<br>`, `</p>`, `</div>`, `</tr>` разделяют строки, `</td>` и `</th>` —
ячейки (` | `), `&nbsp;` становится обычным пробелом, а надстрочный индекс
отделяется кареткой: `ст. 5<sup>1</sup>` → `ст. 5^1`. Вместе с этим
`ПРАВИЛО_ОТПЕЧАТКА` поднято с `strip_html/1` до `strip_html/2`.
Принято 07.09.2026, этап 03.

**Почему это не косметика.** Прежняя нормализация отдавала `ст. 5<sup>1</sup>`
как `ст. 51`. Статья 5¹ и статья 51 — **разные нормы**, и разница здесь не
в оформлении: инструмент выдавал одну под видом другой, а `hash_текста`
эту подмену заверял. Это первый способ соврать из пяти («норма без редакции»
в его тяжёлой форме — норма не та вовсе), и он единственный, где ложь
скреплена нашей же печатью.

Три остальных состава мельче и того же рода: `<br>` и `</td>` склеивали
строки и ячейки табличных норм, `\xa0` жил внутри цитаты и ломал поиск по ней.

**Почему каретка, а не `¹`.** Юникодный надстрочный знак существует не для
всего: индексом бывает не только цифра, а надстрочных кириллических букв
в юникоде нет вовсе. Форма, работающая для части случаев, дала бы ровно
прежний дефект на остатке — молча. Каретка читается и человеком, и любым
последующим разбором, и не притворяется частью текста «Гаранта».

**Что меняется для того, у кого цитата уже в документе.** Отпечаток той же
нормы теперь другой: разделители ячеек и каретка входят в хешируемый текст.
Сверка старой цитаты с новой выдачей **не сойдётся**, и это правильное
поведение — расхождение существовало и раньше, просто было невидимым.
Именно ради этого правило отпечатка и версионируется: `strip_html/1`
в `provenance` старой цитаты говорит, каким текстом её считали.

**Граница.** Кэш `search` переживает смену нормализации: записи, сделанные
под `/1`, до истечения суток отдают заголовки прежней формы. Провенансу это
не вредит — заголовки перечня не хешируются и `hash_текста` не несут, — но
сутки выдача смешана по форме. Отдельная инвалидация кэша не делалась
сознательно: это правка сверх наряда, а вреда, который она предотвращает,
нет.

**Дополнено в тот же день, по невыданной визе `provenance-guard`.** Правка
в первой редакции заменяла прежнюю ложь меньшей, но **необъявленной**:
каретка и ` | ` — наши знаки, а `strip_html('x | y')` отдаёт `'x | y'`, то
есть вход и выход неразличимы, и читатель вправе принять наш разделитель
за вертикальную черту из текста нормы. Отсюда два добавления, оба
обязательные:

* оговорка о нормализации и описания `garant_article` / `garant_document`
  **называют оба знака** как наши, а не как разметку базы;
* там же сказано держателю прежней цитаты: отпечатки под разными версиями
  правила **не сравниваются**, совпадение хеша под разными версиями ничего
  не доказывает, а цитата, выданная под `strip_html/1` и содержавшая
  надстрочный индекс или таблицу, **могла быть искажена**. Это неприятная
  строка, и она обязательна: документ у человека уже подан, а механизма,
  который сообщил бы ему об этом, в продукте нет.

**Имя ключа оговорки — `_предупреждение`, не `_неоднозначность`.** В контуре
ровно одна идиома этого назначения: она названа в `.claude/rules/provenance.md`
и в описаниях `search`, `document`, `article`, `practice`. Клиент — в том
числе живой ИИ-клиент, — приученный поднимать `_предупреждение` наверх,
незнакомого ключа не покажет вовсе. Оговорка, которую никто не видит, — это
не оговорка; тот же класс, что «оговорка, осевшая во внутреннем словаре».
`_период_на_дату` остаётся отдельным ключом-фактом.

## 27. Версия правила отпечатка — метка контракта, а не счётчик правок

**Решение.** `ПРАВИЛО_ОТПЕЧАТКА` поднимается тогда, когда нормализация текста
расходится с последней **выпущенной** версией правила. Внутри одного
невыпущенного шага версия не поднимается повторно, сколько бы правок
нормализации в него ни вошло. Выпущенной на 07.09.2026 является одна —
`strip_html/1`; `strip_html/2` в момент принятия решения не выпущено ни разу:
репозиторий не опубликован, тега нет, правка лежит в некоммиченном дереве.
Принято 07.09.2026, этап 03.

**Почему.** Версия правила отвечает ровно на один вопрос: **одинаково ли
посчитан текст у меня и у того, чья цитата уже лежит в документе.** Она
существует для держателя `provenance`, а не для истории разработки. Если
поднимать её на каждую правку внутри невыпущенного шага, у номера появятся
значения, которых ни у кого никогда не было на руках, и вопрос «одинаково ли
посчитано» перестанет иметь ответ: расхождение версий будет означать то ли
разную нормализацию, то ли разные дни работы.

**Как решение появилось — это существеннее самого решения.** `test-author`
поставил тест, требующий подъёма версии вместе с изменением поведения, и
пометил его как **несогласие с прямой отсылкой к tech-lead**, а не подогнал
под код. `python-dev` версию не поднял и назвал причину. Стык поднялся наверх
за один прогон вместо того, чтобы раствориться в чьей-то сдаче. Ровно ради
этого тесты и пишутся отдельным контекстом.

**Свойство, которое сторожится, при этом не потеряно.** Формулировку получил
тест, а не версия: сторож краснеет на сочетании «поведение отличается от
зафиксированного эталона выпущенной версии» **и** «`ПРАВИЛО_ОТПЕЧАТКА` равно
версии этого эталона». Эталон выпущенного поведения лежит фикстурой — вход
и выход под `strip_html/1`, со всеми его дефектами: склейка `<br>`, склейка
ячеек, `ст. 51`, `\xa0`. Отсюда: возврат склейки без понижения версии —
красный; изменение нормализации при `strip_html/1` — красный; следующая
правка после выпуска `/2` — красный, пока версию не поднимут.

**Граница.** Решение о том, выпущена ли версия, принимает не автор правки:
выпуск — это тег и публикация, а не «мы уже почти». Сомнение трактуется
в пользу подъёма: лишняя версия делает сверку невозможной, недостающая —
делает её ложной, и второе хуже.

## 28. Правку, меняющую выдачу, визирует не автор, и виза читает код, а не сдачу

**Решение.** Правка в `client.py`, `server.py` или `endpoints.json` не
коммитится, пока `provenance-guard` не дал визу, и виза выносится **прогоном
на вырожденных входах**, а не чтением сдачи исполнителя. Исполнитель не
коммитит сам: он кладёт правку в рабочее дерево и называет, что сделал.
Принято 07.09.2026, этап 03.

**Почему — счёт, а не принцип.** 07.09.2026 одна правка выдачи прошла
**пять** заходов визы. Четыре раза виза не давалась, и вот что она находила:

1. каретка и разделитель ячеек вставлены нами и нигде не названы — читатель
   не отличит наш знак от знака акта;
2. оговорка утверждала «действие редакции прерывалось» как факт — а докстрока
   того же файла честно называла это прочтение непроверенным; `действует_с`
   при этом занижал срок действия нормы;
3. третья копия перечня знаков осталась в докстроках `server.py` — с неверным
   числом и с фразой, прямо отрицающей новый текст клиента; докстроку модель
   читает **раньше** ответа и пересказывает своими словами;
4. `_разрыв_в_действии` отвечал «разрыва нет» там, где посчитать нечем:
   при убывающем порядке периодов настоящий перерыв уезжал без оговорки;
5. найденный разрыв побеждал неизвестность, а выбор из нескольких периодов,
   покрывающих дату, оставался немым.

**Три из пяти были внесены самой правкой, а не унаследованы.** Это главное
в решении: правка, чинящая ложь, порождает новую ложь **чаще**, чем правка,
чинящая падение, — потому что предмет здесь не поведение программы, а
утверждение о мире, и его легко сделать чуть увереннее, чем позволяет знание.

**Почему именно отдельный контекст.** Автор читает своё намерение. Он знает,
что имел в виду «прерывание» как гипотезу, и не видит, что текст утверждает
его как факт. Разделение ролей здесь не бюрократия: ни одну из пяти находок
нельзя было получить, перечитав собственную правку, и ни одна не пришла бы
из отчёта — все пять сформулированы как **форма входа с дословным выводом**.

**Что виза обязана делать, а не может.** Обязана: гонять вырожденные входы
(пустой элемент, нечитаемая дата, обратный порядок, перекрытие, смешанная
форма) и сверять текст, уезжающий пользователю, с тем, что код действительно
знает. Не может: подтвердить поведение на живой базе — подписки в среде
разработки нет, и всё сетевое остаётся непроверенным по определению.

**Граница.** Решение не распространяется на правки, не меняющие выдачу:
пути, конфигурация, пульт, установщики. Там виза — `constraint-guard` или
`release-gate` по предмету. И оно не отменяет ворот: виза говорит «выдача
не врёт», а не «этап готов».

**Дополнено по итогам пятой визы.** Правка копилась в рабочем дереве все
пять заходов — и это оказалось отдельной ценой. На пятой визе проверяющий
не смог механически подтвердить, что ветви, объявленные неизменными,
действительно неизменны: в `HEAD` этой функциональности нет вовсе,
промежуточных коммитов между визами нет, и сверить было не с чем. Пришлось
довольствоваться поведением и внутренней согласованностью, что слабее дифа.

Отсюда добавление к порядку: **правка коммитится сразу, как только виза
по ней дана**, даже если следующая виза ещё впереди. Тогда каждый следующий
заход сверяет диф, а не пересказ, и «текст прежний» становится проверяемым
утверждением, а не обещанием.

**Второе дополнение, 07.09.2026: проба обязана воспроизводить тот самый путь.**
Обработчик `SIGTERM` был проверен пробой, поднимавшей сигнал из простаивающего
`select`, — и проба прошла. Дефект был в другом месте: `_Остановка` наследовала
`Exception`, а `socketserver` ловит `except Exception` вокруг обработки запроса,
и сигнал, пришедший **в окно обработки**, проглатывался. В простое этого окна
нет по построению, поэтому проба не могла его увидеть, сколько бы раз её
ни повторяли.

Отсюда правило для проб: проба ставится не на «работает ли механизм вообще»,
а на **состояние, в котором механизм должен сработать**. Демон, который что-то
делает, — не то же самое, что демон, который простаивает; страница, которую
разбирают, — не то же, что страница, которой нет. Если состояние трудно
воспроизвести, это довод в пользу пробы, а не против неё: именно там и живут
дефекты, которых не видно.

И контроль в обратную сторону обязателен: **проба, которая не краснеет
на заведомо сломанном коде, ничего не измеряет**. За этот этап так проверялись
все перечисления — старый примитив покрытия давал 1332 ложных «редакция
не найдена», наследник `Exception` давал проглатывание, снятая остановка
потоков давала зависшие потоки. Без этого контроля зелёная проба означает
только то, что она зелёная.

## 29. Зелёным называется только доказанное; для «ещё не наступило» есть пятый значок

**Решение.** В `garant doctor` зелёный значок ставится только там, где
состояние **проверено этим прогоном**. Пункт, который ничего не проверяет,
и пункт, чьё состояние законно ещё не наступило, получают нейтральный
значок `·` (в терминале без юникода — `[-]`). Красный по-прежнему требует
команды починки: `_пункт` роняет прогон, если её нет. Принято 07.09.2026,
этап 03.

**Почему это правило, а не четыре заплаты.** За один этап один и тот же
дефект нашёлся **четыре раза**, каждый раз другой ролью и в другом месте:

* «версия пакета» — зелёная галочка у пункта, который ничего не проверяет;
* `keepalive` — жёстко зелёный значок, а исход подставлялся в текст: неудачный
  последний keepalive выглядел как удачный;
* «отпечаток: не снят» — зелёный, потому что `расхождение()` при отсутствующем
  файле возвращает пустой список, неотличимый от «снят и сошёлся»;
* `garant login` — «✓ вход завершён» печаталось, не глядя на ключ `вошли`
  (не `doctor`, но ровно тот же приём).

Четыре случая одного вида — это не невнимательность исполнителей, а
отсутствующее правило. Зелёный цвет здесь не украшение: `doctor` существует,
чтобы человек, у которого не работает, узнал, **что именно** не работает.
Ложное зелёное отнимает у него единственный инструмент и отправляет искать
поломку там, где её нет.

**Почему «не снят» не красный.** Красный обещает починку и требует команды.
Отпечаток появляется при первом входе — до него его законно нет, чинить
нечего, и красная строка с командой была бы враньём в другую сторону:
человек пошёл бы исполнять команду, чтобы устранить не-поломку. Отсюда
третье состояние, а не два.

**Что было бы иначе.** Оставить два значка и «просто не ошибаться» — четвёртый
заход на те же грабли; три предыдущих показали, что это не работает.
Сделать «не наступило» отдельным цветом сверх пяти — развилка, которую кто-то
однажды не обработает; пяти хватает.

**Проверяемое условие для теста.** Не «у пункта X правильный значок», а общее:
**ни один пункт `doctor` не зелёный, пока состояние не доказано прогоном.**
Все четыре случая нашлись бы им сразу; ни один не находился четырьмя частными
тестами, потому что частных тестов и не было.

## 30. Утверждение о факте делается там, где факт считается

**Решение.** Если в контуре есть код, вычисляющий факт, то **всякий** текст,
утверждающий этот факт пользователю, обязан опираться на тот же вызов.
Вынести общую формулировку в константу — недостаточно: расходится не текст,
а условие, при котором он произносится. Принято 07.09.2026, этап 03.

**Почему — четыре случая за один этап, все одинаковые:**

* перечень знаков нормализации жил в `client.py` и **третьей копией**
  в докстроках `server.py`: число «два» устарело в тот же день, когда
  появился третий знак;
* прочтение «акт приостанавливали» стояло хеджированным в `client.py`
  и причинным — в докстроках `revisions`/`revision_on_date`;
* оговорка о периодах срабатывала по условию «периодов два и больше»,
  а провенанс на тех же данных считал смежность и молчал: одна редакция,
  одни данные, два разных ответа на вопрос «был ли перерыв»;
* README описывал ключи установщика своими словами и разошёлся с ними
  **три раза подряд**.

**Механика ошибки одна.** Автор выносит формулировку в общее место и считает
задачу закрытой — «утверждение физически одно». Но утверждение состоит из двух
частей: **что сказано** и **когда это говорится**. Вынос закрывает первую
и оставляет вторую копией. Дальше расчёт уточняют в одном месте (смежность
стали считать), а условие в другом остаётся прежним — и текст начинает
произноситься там, где посчитанный факт ему противоречит.

**Что делать вместо.** Место, произносящее утверждение, зовёт ту же функцию,
что и место, его вычисляющее, и ветвится по её результату. Если функции нет —
она заводится до, а не после. Если утверждение по природе непроверяемо
(«почему периодов бывает несколько»), оно остаётся хеджем — и тогда хедж
тоже живёт в одном месте.

**Проверяемое условие для теста.** Не «текст такой-то», а **два места дают
один ответ на один вопрос на одних данных**. Частные тесты этот класс
пропустили дважды: они сверяли текст с ожиданием, а не два места между собой.

**Граница.** Решение не требует единственности текста ради единственности:
докстрока инструмента и ключ в ответе законно говорят разными словами и
разной длины. Требуется единственность **условия** и несопротиворечивость
утверждений. Докстрока, которая по природе не может ветвиться, обязана
говорить слабее ключа, а не сильнее.

## 31. Утверждение, стоящее на нашем непроверенном прочтении, называет это вслух

**Решение.** Там, где вывод инструмента опирается не на данные «Гаранта»,
а на **наше прочтение** этих данных, вывод сопровождается атрибуцией: чьё
это прочтение и что оно на живой базе не проверено. Текст атрибуции живёт
в одном месте (константа) и используется всеми, кто её произносит.
Принято 07.09.2026, этап 03.

**Случай, на котором правило появилось.** Периоды действия редакции
`по 31.12.2020` и `с 01.01.2021` мы считаем смежными — то есть срок
непрерывен. Но это верно **только при включительном** чтении границы,
а как её читает сам «Гарант», не проверено: подписки в среде разработки нет.
При исключающем чтении 31.12.2020 не покрыт ничем, и это дыра в действии
нормы длиной в сутки.

Случай `по 31.12` / `с 31.12` — другой: там непрерывность верна при любом
чтении. До 07.09.2026 оба случая давали **побайтово одинаковый** текст
«Действие нормы между ними не прекращалось», и читатель не мог отличить
утверждение, стоящее на арифметике, от утверждения, стоящего на нашей
трактовке.

**Почему направление ошибки решает.** В `revision_on_date` то же прочтение
даёт **лишнего** кандидата — избыток сомнения, безвредно. В оговорке
о смежности оно сомнение **снимает**: «не прекращалось» — утверждение
о силе нормы. Отсюда общее: прочтение, которое добавляет сомнение, можно
не атрибутировать; прочтение, которое сомнение снимает, атрибутируется
всегда. Второе — это утверждение о мире, сделанное нашими руками.

**Практическое следствие для кода.** Различай неизвестность и знание там,
где различие есть: пустая граница периода — бессрочность (так её пишет
«Гарант»); **неразобранная** граница — незнание, и молча приравнивать её
к бессрочности нельзя, иначе кривая строка превращает истёкший период
в действующий поныне.

**Граница.** Правило не требует обвешивать оговорками всё. Оно требует
различать три вещи, которые легко слить: что сказала база, что посчитал
код, и что мы предположили о базе. Первые две называются фактом; третья —
всегда с атрибуцией.

## 32. Прогон на версии окружения не есть прогон на минимальной поддерживаемой

**Решение.** Утверждение «тесты зелёные» действительно только вместе
с версией интерпретатора, на которой прогон был. Прогон на **минимальной
поддерживаемой** версии (та, что объявлена в `pyproject.toml` и пиньётся
в CI) обязателен там, где правка касается процессов, потоков, замков или
чего-либо, что зависит от внутренностей стандартной библиотеки.
Принято 07.09.2026, этап 03.

**Случай.** `daemon.py` завёл у наследника `threading.Thread` атрибут
`_stop` — событие остановки. Имя совпало с **приватным методом** самого
`Thread`: `join()` идёт через `_wait_for_tstate_lock()` → `self._stop()`,
и на python 3.12 это `TypeError: 'Event' object is not callable`. На 3.14
внутренности другие, и падения нет.

Один и тот же коммит, две версии:

* python 3.12 — версия, объявленная минимумом и стоящая в CI:
  `1 failed, 214 passed, 1 skipped, **12 errors**`;
* python 3.14 — версия рабочей машины: `1 failed, 226 passed, 1 skipped`.

**Все сдачи этапа с числом «224 passed» были верны про свою машину
и ложны про CI.** Причём ни одна из них не соврала: каждый исполнитель
гонял то, что у него стоит, и честно называл число. Не хватало не
добросовестности, а версии рядом с числом.

**Что делать.** Число проходов сопровождается версией интерпретатора.
Правка, трогающая процессы, потоки, замки, сигналы, кодировки или пути,
проверяется **дополнительно** на минимальной версии — временный venv
на неё создаётся одной командой и машину не меняет.

**Почему это нашлось только сейчас.** Дефект жил с момента появления
`BrowserWorker` и не проявлялся, потому что все прогоны шли на версии
рабочей машины. Нашли его **ворота**, а не разработка, — и нашли ровно
потому, что готовили чистую установку и полезли в версию, объявленную
пользователю. Это довод в пользу ворот как отдельной роли: они смотрят
на продукт глазами того, кто его ставит, а не того, кто его писал.

**Граница.** Требовать прогона на всех поддерживаемых версиях при каждой
правке — цена больше пользы. Минимальная обязательна, потому что она
объявлена пользователю и стоит в CI; остальное — по предмету правки.

**Дополнено по итогам виз того же дня.** У правила есть неочевидное следствие
про сами проверки: **проверка, сверяющаяся с внутренностями стандартной
библиотеки, на новой версии слепа к дефектам старой.** `constraint-guard`
искал другие перекрытия приватных имён и сверял их с `dir(threading.Thread)`
**локального 3.14** — а `_stop` там уже не существует, `getattr` возвращает
`None`. То есть проверка, которой ловят этот класс, на 3.14 не поймала бы
исходный дефект вовсе.

Отсюда: сторож на такой класс обязан гоняться **на минимальной версии**,
и в CI это стоит одного прогона, а не глаз. Проверять надо не «нет ли
пересечения со списком имён, который я помню», а «нет ли пересечения
с `dir()` того интерпретатора, на котором идёт прогон».

**Уточнение масштаба, сделанное `constraint-guard` и принятое.** В бою
`Thread.join()` до сломанного имени не доходил: поток создан `daemon=True`,
а `threading._shutdown` daemon-потоки не join-ит. `TypeError` был виден
только тестам, которые join-ят явно. Починка верна и нужна, но продуктовый
путь на этом атрибуте как на методе не стоял — и говорить, что «демон
не останавливался у пользователей», было бы неправдой.

## 33. Число, от которого зависит утверждение, живёт в одном месте — и связь выражается кодом

**Решение.** Если текст или комментарий утверждает что-то о числе («потолок
держится ниже, чем ждёт пульт»), само число живёт в одном месте, а связь
между числами выражается **вычислением**, а не совпадением литералов
и не обещанием в комментарии. Тексты, называющие число пользователю, берут
его оттуда же и не пересказывают прописью. Принято 07.09.2026, этап 03.

**Случай.** `daemon.py` держал `ПОТОЛОК_УБОРКИ_СЕК = 10` и комментарий:
«потолок держится заведомо ниже того, сколько ждёт пульт». Само «сколько
ждёт пульт» — `15` — лежало в `cli.py`, и там же **третьей копией** стояло
«до пяти минут» прописью — то же самое, что `ПОТОЛОК_ВХОДА_СЕК = 300`
в `protocol.py`.

Снизив 15 в `cli.py`, автор молча делал комментарий в `daemon.py` ложным,
и `garant stop` начинал объявлять зависшим демона, который штатно прибирается.
Ни один тест этого не поймал бы: оба файла синтаксически верны, оба числа
осмысленны, неверно только отношение между ними.

**Как сделано.** В `protocol.py`:

```python
ПОТОЛОК_ОСТАНОВКИ_СЕК = 15
ПОТОЛОК_УБОРКИ_СЕК = ПОТОЛОК_ОСТАНОВКИ_СЕК - 5
```

Отношение стало структурным: снизив 15, автор снижает и второе, и утверждение
остаётся верным без чьей-либо бдительности.

**Почему это не то же, что решение 30, а его частный вид.** Решение 30 про
утверждения о фактах, которые код считает. Здесь факт — не вычисляемое
свойство мира, а **наша собственная настройка**, и потому лечится строже:
не «спроси у того, кто считает», а «считай из одного числа».

**Подводный камень, из-за которого правка не сводится к переносу.**
`cli.py` не импортировал `protocol` вовсе, и «пять минут» жили в нём прописью
третьей копией. Половина такой правки хуже целой: она выглядит закрытой.
Это же общее правило для сведения дубликатов — сводить все копии сразу
или не начинать.

**Что осталось незакрытым и названо.** Вычитание не охраняет себя от
вырождения: при `ПОТОЛОК_ОСТАНОВКИ_СЕК <= 5` потолок уборки станет нулём
или отрицательным, и ожидание не сработает вовсе. Запас в 5 секунд взят
по факту прежних чисел, а не измерен: сколько демону нужно на закрытие
браузера — вопрос живой приёмки.

**Дополнено 08.09.2026.** Охрана вычитания добавлена: `protocol.py` роняет
`ValueError` на импорте при `ПОТОЛОК_УБОРКИ_СЕК <= 0`, и текст исключения
называет оба числа. Через `max()` нижнюю границу не поднимали: тогда потолок
уборки сравнялся бы с потолком остановки и тихим стало бы уже обещание
«демон прибирается раньше, чем пульт перестаёт ждать». Чего охрана не ловит,
названо в ней самой: «положительно, но мало» (при шести секундах уборке
остаётся одна) проходит молча; сторожится ровно отмена ожидания. Запас
по-прежнему выбран, а не измерен — измеряет пункт 7б приёмки. Проверено
пробами на копии: потолки 4 и 5 роняют импорт, 6 и 7 проходят
(визы `constraint-guard` 07–08.09, пробы на копии вне дерева). Отдельно принято и не чинится:
`ПОТОЛОК_ВХОДА_СЕК // 60` в тексте отказа `garant stop` округляет вниз —
при 300 даёт верные «5 мин», при значении, не кратном 60, текст округлит;
связь числа с источником структурная, точность — нет.

## 34. Публикация до живой приёмки — решение владельца; условие 3 не снимается, а называется

**Решение.** Репозиторий публикуется одним коммитом **до** того, как живая
приёмка `docs/ACCEPTANCE.md` пройдена. Условие 3 ворот публикации при этом
не снято и командой снято быть не может: его снимает владелец на втором
компьютере, поставив пакет с публичного адреса и пройдя пункты 1, 2, 3, 5,
7, 7а, 7б и 8. До этого этап 03 не закончен. Принято 07.09.2026 промтом
этапа 03: владелец разрешил публикацию прямо и сказал, что проверять будет
сам, на другой машине.

**Почему порядок обратный тому, что писали `PUBLICATION.md` и
`ACCEPTANCE.md`.** Оба документа держали правило «сначала приёмка, потом
push», и держали не зря: чистой машины у команды нет, а первый читатель
не должен проверять установку за нас. Но единственная чистая машина, на
которой владелец может пройти приёмку, — второй компьютер, и ставить туда
он будет с публичного адреса, как посторонний. Приёмка на второй машине
**и есть** установка с публичного адреса, и сделать её до публикации нельзя.
Правило и порядок фаз спорили друг с другом; выбрал владелец.

**Что это стоит и чем цена снижена.** Первое впечатление не отыгрывается:
между push и приёмкой репозиторий открыт, и если установка не доходит до
конца, первым это увидит не владелец. Цена снижена, не убрана: фаза E этапа
проверяет установку с публичного адреса в изоляции здесь, до того как её
увидит владелец там; тег `v<версия>` ставится на тот же коммит; условие 3
в таблице `PUBLICATION.md` по-прежнему помечено «вами» и по-прежнему
единственное говорит о готовности контура.

**Что меняется в документах.** `ACCEPTANCE.md` больше не говорит
«репозиторий не публикуется», а называет порядок по факту; `PUBLICATION.md`
в шаге 6 говорит, что решение принято и когда снимается запрет push.
Всё остальное — пять условий, сжатие до push, идентичность коммита —
остаётся как было.

**Чего решение не делает.** Не отменяет решение 19 (сжатие до push), не
снимает условие 5 и не говорит, что контур готов.

## 35. Пульт судит об остановке по смерти процесса, а журнал после остановки читается с диска

**Решение.** `garant stop` возвращает успех только тогда, когда процесс
демона исчез, а не когда он перестал отвечать по HTTP. Исходов три, и каждый
назван в тексте: процесс ушёл (код 0; текст называет PID, порт, секунды
и отсылает к `garant logs`, потому что закрылся ли браузер, пульт не видит);
демон замолчал, но процесс к потолку жив (код 1; `daemon_port` не снимается —
это единственный след того, кто держит профиль); демон продолжает отвечать
к потолку (код 1; окно входа). `garant logs` при недоступном демоне читает
`logs/daemon.log` с диска — тот же файл, что отдаёт эндпоинт `/logs`, —
и печатает пометку об этом в stderr; без файла отказывает с командой
`garant start`. Принято 08.09.2026, этап 03.

**Случай.** Виза `constraint-guard` 07.09 на диф остановки не была дана по
ограничению 2: новый текст успеха честно говорил «закрылся ли браузер, пульт
не видит — ответ в `garant logs`», а `garant logs` ходил только по HTTP
к демону, который только что остановили, и отвечал «демон не отвечает —
поднять: `garant restart`». А `restart()` принимал код успеха от `stop()` как
разрешение немедленно поднимать нового демона, тогда как на POSIX старый
процесс после сигнала ещё до `ПОТОЛОК_УБОРКИ_СЕК` секунд держит замок
профиля: замок снимается смертью процесса, а не закрытием слушателя.
Новый демон упирался бы в занятый профиль, выходил, и `обеспечить_демона`
через 90 секунд отдавал бы «демон не поднялся».

**Почему смерть процесса, а не молчание порта.** Ограничение 2 держит
замок ОС на профиле, и снять его может только смерть владельца. Молчание
порта наступает раньше: демон снимает слушателя и только потом ждёт
закрытия браузера. Единственный признак, после которого профиль
действительно свободен, — процесса больше нет.

**Почему пометка в stderr.** Вывод `garant logs` читают как сам журнал —
глазами и программами. Подмешивать в него строку о том, откуда он взят,
значит подделывать журнал; stderr — то место, где пульт говорит от себя.

**Что осталось незакрытым и названо.**
* `_имя_процесса` возвращает `None` и когда процесса нет, и когда о нём
  не удалось спросить (сбой `tasklist`/`ps`). Пульт их не различает.
  Монопольность это не ломает — её держит замок ОС в `занять_профиль()`;
  цена ложного `None` — ложный отчёт пульта и отказ следующего демона
  «профилем уже владеют», а не два браузера на один профиль.
* Ранний путь `stop()` («демон не отвечает — останавливать нечего», код 0)
  не спрашивает, жив ли процесс из `daemon_port`; `restart()` через него
  поднимает нового демона. Путь пришёл из HEAD, этой правкой не тронут —
  отдельный наряд.
* После молчания порта процесс опрашивается подпроцессом каждые полсекунды,
  до тридцати запусков за потолок; на медленной машине потолок выдерживается
  приблизительно. Замера нет.
* Настоящая остановка живого демона — реальный сигнал, смерть процесса,
  снятие замка, `restart` в освободившийся профиль — здесь не проверялась
  и не может быть: это пункт 7б живой приёмки.

## 36. Пустое по-питоновски значение границы периода читается как отсутствие границы; непустое нестроковое — как граница, которую прочесть нечем

**Решение.** Границу периода действия («с» и «по» из `activity[].from`/
`.to`) читает один примитив, `_граница_текстом`, — и для расчёта, и для
каждого рендера в выдаче. `None`, пустая и пробельная строка, `0`, `False`,
`[]`, `{}` — границы нет: для «по» это «бессрочно», для «с» — «?».
Непустое нестроковое (число, список, объект) — граница есть, прочесть её
нечем: в тексте она показывается в форме JSON, а не Python-repr, и рядом
стоит оговорка. Оговорка о заверяющей дате (`_оговорка_о_заверяющей_дате`)
отвечает на другой вопрос — «дата ли то, что стоит в `действует_с`» — и
молчит только на `None`, пустой строке и строке из одних пробелов; на `0`
или `[]` она стоит, потому что значение видно. Принято 08.09.2026, этап 03.

**Случай.** Визы `provenance-guard` 07–08.09 на диф оговорки о дате
(`client.py`): новый примитив читал `0`/`[]`/`{}` как «0»/«[]»/«{}», и
период `{с: 0, по: 0}` становился значащим вопреки собственной докстроке;
четыре рендера «по» читали то же значение как «бессрочно»; после того как
рендеры «по» провели через примитив, пять рендеров «с» остались прежними,
и один ответ печатал одно значение двумя написаниями — `{'d': 1}` в перечне
периодов и `{"d": 1}` в оговорке о дате, а пробельная строка слева читалась
«пусто», справа — «бессрочно». Перебор входами (102 клетки на слот) после
правки — 0 расхождений расчёта с рендером.

**Почему это прочтение чужого формата, и что оно стоит.** По образцу решений
24 и 31: «Гарант» пишет бессрочность пустым «по», а какие ещё формы приходят
в границах — не видел никто, весь перебор синтетический. Прочтение «пустое
по-питоновски = границы нет» снимает сомнение, то есть делает утверждение
о силе нормы («бессрочно»), и потому названо здесь, а не только в докстроке.
Проверяет его владелец: вопрос 8 пункта 7а приёмки расширен до «какие формы
приходят в границах, дословно и с типом».

**Что осталось незакрытым и названо.** `revision_on_date` перебирает
`периоды` сырыми, не через `_значащие_периоды`: шумовой элемент
`{с: 0, по: ""}` становится кандидатом и заставляет инструмент ответить
там, где иначе была бы ошибка «редакция на дату не найдена»; ответ несёт
две оговорки. Поведение из HEAD, направление — избыток сомнения; не чинилось.

## 37. Набор правил ruff зафиксирован в `pyproject.toml`; CI не полагается на умолчания линтера

**Решение.** В `pyproject.toml` стоит `[tool.ruff.lint] select = ["E4",
"E7", "E9", "F"]` и `per-file-ignores "tests/**" = ["F811"]`. Правило
`.claude/rules/python.md` «линтера в проекте нет» снято: `ruff` объявлен
в dev-зависимостях с этапа 02 и гоняется в CI до тестов. Принято 08.09.2026,
этап 03.

**Случай.** CI ставит `pip install -e ".[dev]"`, то есть свежий `ruff`, и
гоняет `python -m ruff check src tests` **до** pytest. Конфигурации в
репозитории не было. `ruff` 0.16.6 без неё включает около четырёхсот правил
и даёт 555 находок на HEAD; классический набор даёт 52 (35 — F811 в тестах,
14 — F401, 2 — E702, 1 — F841). CI ни разу не бежал, потому что remote нет:
первый push был бы красным по шагу, который идёт раньше тестов, и до тестов
CI не дошёл бы.

**Почему классический набор, а не умолчания.** Код писался под него;
расширять набор — отдельный наряд с чтением каждого правила, а не побочный
эффект версии инструмента, поставленной в чужом CI в чужой день.

**Почему F811 игнорируется в `tests/`.** Фикстура pytest импортируется из
`test_paths.py` и затем называется параметром теста — для линтера это
переопределение неиспользованного имени, для pytest — единственный способ
получить фикстуру из другого файла без `conftest.py`. Перенос фикстур
в `conftest.py` — отдельный наряд (правило `tests.md`: фикстура живёт
в `test_paths.py` и только там).

**Что осталось.** Набор E4/E7/E9/F проверяет синтаксис и имена, не стиль.
Классические находки закрыты правкой: неиспользуемые импорты, две точки
с запятой, одна неиспользуемая переменная. Прогон CI на двух ОС — после
публикации; здесь проверена только команда CI локально, `ruff` 0.16.6.

## 38. Совет в точке отказа обязан быть исполним в том состоянии, в котором печатается

**Решение.** Текст, который печатается на отказе, называет команду, которая
чинит ровно то состояние, в котором этот текст напечатан, — а не самое
частое состояние с тем же симптомом. Если код различить состояния не может,
он различает их прежде, чем советовать; если различить нельзя в принципе,
совет называет оба случая и порядок их проверки. Принято 08.09.2026,
этап 03.

**Случай.** Ворота фазы B (живой прогон установки в изоляции): ветка
`install.ps1` «каталог с командами пока не в PATH этой консоли» печатала
«откройте новое окно консоли — PATH там уже правильный» ровно тогда, когда
это не могло быть верно: функция `Обновить-PATH` уже слила в `$env:Path`
обе постоянные ветки реестра, и только после этого команда не нашлась —
значит, её нет и в постоянном PATH, и в новом окне не будет. Пункт `doctor`
«пакет в PATH» в том же состоянии советовал переустановку, которая ничего
не меняет. README давал тот же совет как общий. Человек с `uv` из winget
или scoop, либо со своим `UV_TOOL_BIN_DIR`, ходил бы по кругу из трёх
одинаковых неверных ответов, и первым это увидел бы владелец на втором
компьютере.

**Как сделано.** Установщики и `doctor` различают два состояния: команда
нашлась после слияния PATH — новое окно; не нашлась — сначала команда
менеджера, правящая постоянный PATH (`uv tool update-shell`, для pipx —
`pipx ensurepath`), потом новое окно. `doctor` различает «пакет установлен,
но каталог его команд не в PATH» (сам пульт и есть пакет: `argv[0]` —
файл команды, либо `garant` в каталоге скриптов текущего интерпретатора)
и «пакета нет вовсе» (прежний совет). Пункт остаётся красным и в первом
состоянии — команда по имени действительно не зовётся, а починка у пункта
есть. README называет оба случая тем же порядком.

**Что осталось незакрытым и названо.** `pipx ensurepath` взят как команда
pipx и на этой машине не прогонялся (pipx не установлен). Состояние
«запуск через `uvx --from garant-mcp`» без постоянной установки даёт тот
же совет, хотя `update-shell` там не поможет, — редко, не заявлялось.
`tests/test_советы_несут_команду.py` сторожит только советы с
глаголами-триггерами; новый совет `doctor` покрыт отдельным тестом.

## 39. Однострочник установки срезает метку кодировки сам; опубликованный тег не переносится

**Решение.** Команда установки для Windows в README имеет вид
`& ([scriptblock]::Create((irm …/install.ps1).TrimStart([char]0xFEFF)))`,
а не `irm … | iex`. BOM в `install.ps1` остаётся: без него Windows
PowerShell 5.1 читает файл при запуске как ANSI и ломает кириллицу, включая
имена ключей. Тег `v0.2.0` остаётся на коммите публикации; после починок,
изменивших то, что получает пользователь, версия поднимается до 0.2.1 и тег
ставится на итоговый зелёный коммит. Принято 09.09.2026, этап 03.

**Случай.** Фаза E (установка с публичного адреса в изоляции): единственная
команда, которую README давал пользователю Windows, дословно исполненная,
падала на разборе — `irm` возвращает текст вместе с U+FEFF, для парсера это
не пробел, `[CmdletBinding()]` перестаёт быть первым оператором; код 1,
установлено ничего. Запасной путь «скачать файлом и запустить» при этом
ставил пакет с GitHub до конца. Первый прогон CI на коммите публикации был
красным на обеих ОС (хук молчал под dash — решение 37 его не касалось; два
теста с Windows-зависимостями; кодировка дымового теста); всё закрыто
следующим коммитом, CI зелёный.

**Почему не снять BOM.** Тогда сломается запуск файлом на PowerShell 5.1
у всех, у кого нет PowerShell 7, — то есть у обычного Windows. Срезать BOM
в момент загрузки дешевле и не меняет файл.

**Почему не перенести тег.** Опубликованный тег читают как неизменяемый:
`uv tool install …@v0.2.0` уже мог кому-то поставить ровно тот блоб.
Изменившееся получает новый номер.

**Что осталось незакрытым и названо.** Однострочник проверен из PowerShell
(справка установщика с публичного адреса, код 0, и полный прогон
с ключами изоляции); из cmd.exe дословно не проверялся — README велит
открыть PowerShell. Ветка «uv не найден → установщик Astral» и путь через
pipx не исполнялись ни разу: uv на машине разработки есть. Каталог установки
с пробелами и кириллицей живым прогоном не проверен.
